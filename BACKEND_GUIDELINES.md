# NestJS Backend Development Standards

Цей документ визначає стандарти написання коду для бекенду (NestJS) в межах нашого монорепозиторію. Дотримуйся цих правил для забезпечення безпеки, масштабованості та чистоти коду.

## 1. Архітектура та Розділення Відповідальності (Separation of Concerns)
* **Модульність**: Кожен логічний домен (Auth, Workouts, Users) повинен мати власний модуль (`.module.ts`).
* **Controllers**: Відповідають ВИКЛЮЧНО за HTTP-маршрутизацію, отримання параметрів (Body, Query, Params) та повернення відповідей. **Жодної бізнес-логіки в контролерах!**
* **Services**: Тут живе вся бізнес-логіка та взаємодія з базою даних. Сервіси мають бути незалежними від HTTP-контексту (не повинні знати про `Request` чи `Response`).
* **Dependency Injection**: Завжди використовуй вбудований DI-контейнер NestJS (конструктори класів) для ін'єкції сервісів та репозиторіїв.

## 2. Спільні Інтерфейси (Monorepo Rule)
* **НАЙВИЩИЙ ПРІОРИТЕТ**: Ніколи не створюй інтерфейси даних з нуля на бекенді, якщо вони стосуються клієнта.
* Всі базові контракти (Request, Response, Models) імпортуються з пакета `@athlo/shared`.
* **DTO (Data Transfer Objects)**: DTO-класи на бекенді обов'язково повинні імплементувати (через `implements` або `Omit`/`Pick`) спільні інтерфейси.
  * *Приклад*: `export class RegisterDto implements RegisterRequest { ... }`

## 3. Валідація та DTO
* Суворо використовуй `class-validator` та `class-transformer` для валідації вхідних даних.
* Всі поля в DTO повинні мати відповідні декоратори (наприклад, `@IsString()`, `@IsEmail()`, `@IsOptional()`).
* У файлі `main.ts` має бути глобально увімкнений `ValidationPipe` з налаштуваннями `whitelist: true` (відсікає зайві поля) та `transform: true` (автоматично типізує).

## 4. Безпека та Авторизація
* **Guards**: Використовуй `JwtAuthGuard` для захисту приватних ендпоінтів. 
* За замовчуванням всі маршрути повинні бути захищені (Global Guard), а публічні маршрути (наприклад, логін/реєстрація) мають позначатися кастомним декоратором `@Public()`.
* **Current User**: Для отримання даних авторизованого користувача використовуй кастомний декоратор `@CurrentUser()`, а не діставай їх напряму з `req.user`.
* **Паролі**: Ніколи не повертай хеші паролів у відповідях API (використовуй серіалізацію або виключай поля).

## 5. Обробка Помилок (Error Handling)
* Не використовуй стандартні `Error` або `console.log` для помилок.
* Використовуй вбудовані HTTP-винятки NestJS (`NotFoundException`, `BadRequestException`, `UnauthorizedException` тощо) в сервісах.
* Забезпечуй інформативні повідомлення про помилки (наприклад, `new NotFoundException('Workout with ID 123 not found')`).

## 6. Документація (Swagger)
* Кожен ендпоінт повинен бути задокументований за допомогою декораторів `@nestjs/swagger`.
* **Контролери**: Додавай `@ApiTags('Name')`.
* **Ендпоінти**: Додавай `@ApiOperation()`, `@ApiResponse()` (для успішних і неуспішних відповідей).
* **DTO**: Всі поля DTO повинні бути описані декоратором `@ApiProperty()`.

## 7. Найменування (Naming Convention)
* **Файли**: `[name].[type].ts` (наприклад, `workout.controller.ts`, `workout.service.ts`).
* **Класи**: PascalCase (`WorkoutService`).
* **Методи та змінні**: camelCase (`getWorkoutById`, `workoutData`).
* **Ендпоінти**: Використовуй множину для ресурсів REST API (наприклад, `GET /exercises`, `POST /workouts/:id/sets`).
