РОЗДІЛ 4. РЕАЛІЗАЦІЯ ТА ТЕСТУВАННЯ МОБІЛЬНОГО ЗАСТОСУНКУ ATHLO

4.1. Програмна реалізація серверної частини
Серверну частину застосунку Athlo реалізовано на платформі Node.js мовою TypeScript [11] з використанням фреймворку NestJS версії 11 [13]. Кодова база організована як монорепозиторій під керуванням Turborepo з трьома пакетами: серверного застосунку `apps/api`, мобільного клієнта `apps/mobile` та спільної бібліотеки типів `@athlo/shared`, у якій зосереджено 42 інтерфейси та 7 переліків, спільних для клієнта і сервера. Такий поділ забезпечує єдиний контракт обміну даними між клієнтом і сервером без дублювання визначень типів. Файлову структуру серверного проєкту наведено на рис. 4.1.

Рис. 4.1. Структура файлів серверного проєкту NestJS

Кореневий модуль `AppModule` асинхронно ініціалізує підключення до бази даних PostgreSQL [14] через `TypeOrmModule.forRootAsync` та підключає чотири доменних модулі: `UserServiceModule` (управління користувачами та соціальні взаємодії), `ExerciseCatalogModule` (каталог вправ, обладнання та м'язових груп), `WorkoutsServiceModule` (тренування, шаблони, особисті рекорди та досягнення) і `NutritionServiceModule` (харчування та плани раціону). Кожен з модулів самостійно реєструє власні контролери, сервіси та сутності TypeORM [17], що відповідає принципу інкапсуляції доменної логіки в межах одного модуля.
Внутрішня організація кожного модуля побудована за тришаровою схемою. Контролер описує HTTP-маршрут, валідує DTO та делегує виконання операції відповідному сервісу. Сервіс містить бізнес-логіку та координує роботу з репозиторіями TypeORM, що ін'єктуються через декоратор `@InjectRepository`. Захищені маршрути позначаються декоратором `@UseGuards(JwtAuthGuard)` на рівні класу-контролера, а ідентифікатор поточного користувача витягається з токена через декоратор-параметр `@CurrentUser('id')`. Як приклад, контролер тренувань має такий вигляд:

```
@ApiTags('Workouts')
@ApiBearerAuth()
@UseGuards(JwtAuthGuard)
@Controller('workouts')
export class WorkoutController {
  constructor(private readonly workoutService: WorkoutService) {}

  @Post()
  create(@CurrentUser('id') userId: number, @Body() dto: CreateWorkoutDto) {
    return this.workoutService.create(userId, dto);
  }
}
```

Для опису доменної моделі використано 33 сутності TypeORM, кожна з яких відображає одну таблицю реляційної бази даних. Зокрема, структура тренувань складається з двох паралельних ієрархій: відстеження фактичної сесії (`WorkoutEntity` – `LogExerciseEntity` – `LogSetEntity`) та шаблонів для повторного використання (`WorkoutTemplateEntity` – `TemplateExerciseEntity` – `TemplateSetEntity`). Зв'язки між сутностями оформлено декораторами `@OneToMany`, `@ManyToOne`, `@JoinColumn`, а каскадне видалення вкладених записів забезпечується параметром `cascade: true` у власника відносини. Фрагмент опису сутності окремого підходу наведено на рис. 4.2.

Рис. 4.2. Фрагмент опису сутності LogSetEntity з декораторами TypeORM

Авторизація реалізована через JSON Web Token [16] із використанням бібліотеки Passport.js та модуля `@nestjs/passport` [21]. Класи `AuthService.register` та `AuthService.login` виконують ключові операції створення облікового запису та входу. Паролі ніколи не зберігаються у відкритому вигляді: метод `bcrypt.compare` бібліотеки bcrypt [22] виконує порівняння введеного пароля з хешем, обчисленим алгоритмом bcrypt з 10 раундами підсолу. Сама стратегія перевірки JWT-токена реалізована як окремий клас, який реєструється у Passport:

```
@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
  constructor(configService: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      ignoreExpiration: false,
      secretOrKey: configService.getOrThrow<string>('JWT_SECRET'),
    });
  }
  validate(payload: JwtPayload) {
    return { id: payload.sub, email: payload.email };
  }
}
```

Термін дії токена обмежено сімома днями та задано через `JwtModule.registerAsync` із використанням значення змінної середовища `JWT_SECRET`. Усі вхідні DTO декларативно валідуються бібліотекою class-validator [23] за рахунок декораторів `@IsEmail`, `@MinLength`, `@IsInt`, `@IsOptional` тощо. Глобальний `ValidationPipe`, зареєстрований у `main.ts` з опціями `{ whitelist: true, transform: true }`, автоматично відкидає поля, не описані в DTO, і приводить рядкові значення до зазначених типів.
Ключова бізнес-логіка тренувального модуля зосереджена у сервісі `LogSetService`, який після збереження кожного підходу викликає сервіс досягнень для перевірки нових рекордів. Метод створення нового підходу одночасно перевіряє приналежність тренування користувачу та запускає повний перерахунок особистих рекордів вправи:

```
async create(workoutId: number, logExerciseId: number, userId: number, dto: CreateLogSetDto) {
  await this.validateOwnership(workoutId, logExerciseId, userId);
  const set = this.logSetRepository.create({ logExerciseId, ...dto });
  const saved = await this.logSetRepository.save(set);
  await this.achievementService.checkAndUpdateRecords(userId, logExerciseId);
  return this.logSetRepository.findOne({
    where: { id: saved.id },
    relations: { achievement: true },
  });
}
```

Сервіс `AchievementService.checkAndUpdateRecords` повністю перерахує записи `UserExerciseRecord` для відповідної вправи: порівнює максимальну вагу, кількість повторень, обсяг (добуток ваги на повторення), оцінений одноповторний максимум та найкращий час відносно попередніх збережених значень. У разі перевищення хоча б одного з показників відповідному підходу присвоюється прапорець `isPR = true` та зв'язок із новим записом досягнення. Окремо при завершенні тренування система перевіряє розблокування глобальних досягнень за категоріями GLOBAL_WORKOUTS, GLOBAL_SETS, GLOBAL_WEIGHT та GLOBAL_TIME.
У модулі харчування центральною операцією є метод `NutritionLogService.getDailySummary`, який агрегує загальну калорійність та макронутрієнти за всіма прийомами їжі обраної дати. Розрахунок виконується за формулою: внесок одного продукту до калорійності прийому дорівнює добутку калорійності на 100 г з бази продуктів на коефіцієнт `calculatedWeightG / 100`. Споживання води розраховується окремо: цільове значення дорівнює добутку поточної ваги користувача на 35 мл, або встановленому користувачем значенню з налаштувань. Активація плану харчування реалізована у сервісі `MealPlanService.activatePlan` із гарантією одного активного плану на користувача в будь-який момент часу:

```
async activatePlan(userId: number, planId: number) {
  await this.userMealPlanRepository.update(
    { userId, isActive: true },
    { isActive: false },
  );
  const existing = await this.userMealPlanRepository.findOne({
    where: { userId, mealPlanId: planId },
  });
  if (existing) {
    existing.isActive = true;
    existing.startedAt = new Date();
    return this.userMealPlanRepository.save(existing);
  }
  return this.userMealPlanRepository.save(
    this.userMealPlanRepository.create({ userId, mealPlanId: planId, isActive: true }),
  );
}
```

Підключення до бази даних виконується через єдину функцію `getTypeOrmConfig`, яка зчитує рядок з'єднання `DATABASE_URL` з конфігурації та налаштовує SSL-канал з параметром `rejectUnauthorized: false`, необхідним для роботи з керованим сервісом Supabase [20]. Параметр `synchronize: false` гарантує, що схема не змінюється автоматично у виробничому середовищі, а еволюція таблиць здійснюється виключно через міграції CLI TypeORM. Окрім бізнес-логіки, серверний застосунок забезпечує автоматичну генерацію інтерактивної OpenAPI-документації за допомогою `@nestjs/swagger`. Документація доступна за маршрутом `/api/docs`, містить опис усіх контролерів та підтримує авторизацію через Bearer-токен.

4.2. Програмна реалізація клієнтської частини
Мобільну клієнтську частину розроблено мовою TypeScript на платформі React Native [12] версії 0.83.2 із використанням середовища Expo SDK ~55 [15]. Структура клієнтського проєкту відображена на рис. 4.3. Кодова база розподілена між папками `app/` (екрани та маршрути), `features/` (доменні модулі), `components/ui/` (універсальні UI-компоненти), `hooks/api/` (хуки для звернень до сервера), `contexts/` (контекстні провайдери), `constants/` (тема та системні константи) та `api/` (HTTP-клієнт і визначення маршрутів).

Рис. 4.3. Структура файлів мобільного проєкту Expo

Навігаційну модель побудовано на бібліотеці Expo Router [24], яка використовує файлову конвенцію подібно до Next.js. Структура папки `app/` напряму відображається у дерево маршрутів: група `(auth)` містить екрани реєстрації та входу, а група `(app)` об'єднує захищені розділи `(workout)`, `(nutrition)`, `(profile)`. Динамічні сегменти реалізовані через файли `template/[id].tsx` для перегляду шаблону тренування та `[userId].tsx` для перегляду профілю іншого користувача. Такий підхід усуває необхідність ручного оголошення стеків навігації та автоматично формує типобезпечні параметри маршрутів.
Серверний стан у клієнті управляється бібліотекою TanStack Query версії 5 [25]. Усі мережеві операції реалізовано як хуки `useQuery` (читання) та `useMutation` (запис) у папці `hooks/api/`. Бібліотека автоматично кешує відповіді сервера за ключем запиту, відстежує статуси завантаження та помилок, виконує інвалідацію кешу після мутацій. Для локального стану, який не потребує синхронізації з сервером, застосовано штатний механізм React Context: контекст `AuthContext` зберігає поточного користувача та токен, а контекст `ActiveWorkoutContext` утримує стан активної сесії тренування. Відмова від Redux або інших великих бібліотек керування станом аргументована обмеженою кількістю глобальних потоків даних, що не виправдовує накладні витрати на додаткову інфраструктуру.
Взаємодія з сервером здійснюється через єдиний екземпляр HTTP-клієнта, побудованого на бібліотеці Axios [26]. Базовий URL визначається динамічно: у режимі розробки він формується з `expo-constants` на основі адреси Metro Bundler, а у виробничій збірці використовується розгорнутий екземпляр сервера на платформі Render [19]. До екземпляра приєднано два перехоплювачі (interceptors): перший автоматично додає заголовок `Authorization: Bearer <token>`, дістаючи токен зі сховища `expo-secure-store`; другий обробляє відповіді з кодом 401 шляхом видалення токена та виклику зареєстрованого обробника виходу:

```
apiClient.interceptors.request.use(async request => {
  const token = await AuthService.getToken();
  if (token) request.headers.Authorization = `Bearer ${token}`;
  return request;
});
apiClient.interceptors.response.use(
  response => response,
  async error => {
    if (error.response?.status === 401) {
      await AuthService.deleteToken();
      onUnauthorized?.();
    }
    return Promise.reject(error);
  },
);
```

Доменні модулі `features/auth`, `features/workout`, `features/nutrition`, `features/profile` та `features/friends` побудовані за єдиним шаблоном. Кожен модуль складається з папок `components/` (видимі елементи інтерфейсу), `hooks/` (логіка взаємодії з API та локальним станом), `services/` (інкапсуляція операцій, що не залежать від UI) та файлу `types.ts` з власними доменними типами. Як приклад, хук `useFoodPickerScreen` модуля харчування реалізує динамічний перерахунок поживних значень при зміні обраної одиниці виміру або обсягу порції:

```
const calculatedMacros = useMemo(() => {
  if (!selectedFood) return null;
  let factor = 1;
  if (selectedFood.units) {
    const selectedUnit = selectedFood.units.find(u => u.unitId === unitId);
    if (selectedUnit) factor = Number(selectedUnit.conversionFactor);
  }
  const totalGrams = (parseFloat(amount) || 0) * factor;
  const macroFactor = totalGrams / 100;
  return {
    calories: Math.round(selectedFood.calories * macroFactor),
    proteins: Math.round(selectedFood.proteins * macroFactor * 10) / 10,
    fats: Math.round(selectedFood.fats * macroFactor * 10) / 10,
    carbs: Math.round(selectedFood.carbs * macroFactor * 10) / 10,
  };
}, [selectedFood, amount, unitId]);
```

Стан активної сесії тренування інкапсульовано в провайдері `ActiveWorkoutProvider`, який підтримує операції додавання вправ, фіксації підходів та переміщення елементів. Реалізація операції додавання вправи демонструє важливий аспект – уникнення дублювання при повторному виборі тієї самої вправи (порівняння за `logExerciseId`):

```
const addExercise = useCallback((exercise) => {
  setState((prev) => {
    const newExercise = {
      ...exercise,
      order: prev.exercises.length + 1,
      showNotes: false,
      notes: exercise.notes ?? '',
      sets: exercise.sets ?? [{ order: 1, isCompleted: false }],
    };
    const existingIndex = exercise.logExerciseId != null
      ? prev.exercises.findIndex(e => e.logExerciseId === exercise.logExerciseId)
      : -1;
    if (existingIndex >= 0) {
      const updated = [...prev.exercises];
      newExercise.order = prev.exercises[existingIndex].order;
      updated[existingIndex] = newExercise;
      return { ...prev, exercises: updated };
    }
    return { ...prev, exercises: [...prev.exercises, newExercise] };
  });
}, []);
```

Візуальне оформлення інтерфейсу побудоване на власній дизайн-системі, описаній у файлі `constants/theme.ts`. Палітра побудована навколо темного фону (`#0A0906`) та зеленого акценту бренду (`#2BDE6A`), що відповідає вимогам зручності читання в умовах зниженого освітлення (наприклад, у спортивному залі) та типовим стандартам фітнес-сегмента. Окремо визначені шкали відступів за чотирипунктовою сіткою, радіусів заокруглення, розмірів шрифтів та трьох рівнів тіней (карткові, модальні, кнопкові). Для побудови графіків динаміки антропометричних показників та статистики тренувань застосовано бібліотеку react-native-gifted-charts, яка надає компоненти лінійних та стовпчастих діаграм із підтримкою анімацій і налаштовуваних стилів.

4.3. Опис роботи розробленого програмного забезпечення
При першому запуску застосунку користувач потрапляє на стартовий екран авторизації (рис. 4.4). На цьому екрані подано форму входу з полями електронної адреси та пароля, а також посилання на форму реєстрації. У режимі реєстрації користувач додатково вводить повне ім'я та нікнейм. Введені дані валідуються двічі: спочатку на клієнті (формат email, мінімальна довжина пароля), а після надсилання на сервер – на стороні NestJS-обробника. Після успішного входу сервер повертає JWT-токен, який клієнтський застосунок зберігає у захищеному сховищі `expo-secure-store` під ключем `athlo_access_token` і використовує для всіх наступних запитів.

Рис. 4.4. Екран автентифікації користувача

Після успішної авторизації застосунок відображає головний екран тренувань (рис. 4.5). У верхній частині розміщено привітання та коротку інформацію про активну сесію, якщо така є. Нижче подано прокручуваний список останніх проведених тренувань зі стислими підсумками: датою, тривалістю, кількістю підходів та сумарним обсягом піднятої ваги. У нижній частині екрана закріплено навігаційну панель із трьома вкладками – тренування, харчування та профіль, – що забезпечує прямий доступ до основних розділів застосунку. Дві кнопки у верхній частині списку дозволяють розпочати порожню сесію або обрати наявний шаблон.

Рис. 4.5. Головна сторінка вкладки тренувань

Центральним екраном тренувального процесу є сторінка активного тренування (рис. 4.6). Користувач послідовно додає вправи з каталогу через кнопку «Додати вправу» та фіксує їх виконання у вигляді підходів. Для кожної вправи відображається таблиця підходів із полями, що відповідають типу відстеження: вага та повторення для силових вправ, лише повторення – для вправ із власною вагою, тривалість та дистанція – для кардіо-навантажень. Поряд із кожним полем розміщено сірим кольором підказку із значенням попереднього підходу або найкращим власним результатом, що пришвидшує введення даних. Позначення підходу як виконаного відправляє запит на сервер, який після збереження автоматично перевіряє наявність нового особистого рекорду. У разі його встановлення з'являється модальне вікно з повідомленням про досягнення.

Рис. 4.6. Екран активного тренування з виявленим особистим рекордом

Окремою важливою функцією є таймер відпочинку, який автоматично запускається після позначення підходу як виконаного на встановлений у шаблоні час. Перебіг таймера відображається у нижньому перекритті екрана та може бути продовжений або зупинений вручну. Завершення тренування ініціюється кнопкою «Закінчити» з підтвердженням у модальному вікні, де користувач опціонально вказує суб'єктивну оцінку (RPE) та коментарі. Сервер фіксує час завершення сесії, обчислює сумарні показники та запускає перевірку розблокування глобальних досягнень.
Розділ харчування побудований навколо щоденного зведення (рис. 4.7). У верхній частині екрана розміщено блок із загальною калорійністю за день та індикаторами спожитих білків, жирів і вуглеводів. Цільові значення для калорійності та макронутрієнтів беруться з активного плану харчування або з цілей, заданих користувачем вручну, а коли жодне з джерел не задане, блок показує лише спожиті за день показники. Окремий блок відображає поточний обсяг спожитої води зі швидкими кнопками для типових порцій (200, 300, 500 мл) та можливістю задати власний об'єм. Прокручуючи екран вниз, користувач переглядає прийоми їжі, згруповані за типами (сніданок, обід, вечеря, перекус). Стрілки у верхній частині екрана дозволяють переходити між днями для перегляду історії або планування наперед.

Рис. 4.7. Головна сторінка вкладки харчування

Додавання продукту до прийому відбувається на окремому екрані пошуку (рис. 4.8). Текстове поле виконує пошук бази продуктів через серверний ендпоінт із роботою у режимі підвантаження сторінок під час прокручування. Після вибору продукту відкривається картка з полем кількості та випадаючим списком одиниць виміру (грами, мілілітри, штуки, скибки тощо). Будь-яка зміна обраного значення викликає миттєвий перерахунок калорій та макронутрієнтів через коефіцієнт `conversionFactor` обраної одиниці. Якщо потрібного продукту немає в базі, користувач може створити власний запис із вказаною харчовою цінністю на 100 г.

Рис. 4.8. Екран пошуку та додавання продукту до прийому їжі

Розділ профілю об'єднує особисті дані, антропометричні показники, статистику тренувань та соціальні взаємодії (рис. 4.9). На головній сторінці профілю відображається коротка інформація про користувача, кнопки переходу до редагування, статистики, досягнень, календаря активності та екрана друзів. Окрема вкладка «Метрики тіла» містить форму додавання нових записів (вага, відсоток жиру, окружності) та лінійні графіки динаміки кожного показника, побудовані бібліотекою react-native-gifted-charts. Соціальний модуль реалізує надсилання та прийняття заявок у друзі, перегляд публічних шаблонів тренувань інших користувачів та сторінки сторонніх профілів із контролем рівня видимості.

4.4.2.3. Інтеграційне тестування
Для перевірки коректної взаємодії між мобільним клієнтом, серверним застосунком NestJS та керованою базою даних Supabase розроблено вісім інтеграційних тестових сценаріїв, що моделюють повні цикли роботи користувача. Окрім ручних інтеграційних перевірок, серверний застосунок містить один кінець-в-кінець тест на базі бібліотеки Supertest [28], який перевіряє доступність кореневого маршруту та коректну ініціалізацію застосунку. Конфігурація e2e-тестування винесена у файл `test/jest-e2e.json` із власним патерном пошуку `.e2e-spec.ts$` та середовищем виконання `node`. Інтеграційні сценарії повного шляху виконано вручну з використанням окремої тестової схеми у Supabase, що ізолює тестові дані від виробничих.

4.4.2.4. Тестування безпеки
Тести безпеки покривають п'ять критичних аспектів захисту даних. Перший випадок перевіряє коректність хешування паролів: після реєстрації у базі даних зберігається лише bcrypt-хеш, а не пароль у відкритому вигляді. Другий випадок підтверджує відхилення запитів без JWT-токена або з простроченим токеном з поверненням коду 401 Unauthorized. Третій випадок перевіряє ізоляцію даних між користувачами: спроба отримати або змінити тренування іншого користувача за його ідентифікатором повертає 403 Forbidden або 404 Not Found. Четвертий випадок підтверджує дієвість валідації вхідних DTO через бібліотеку class-validator: спроби надіслати поля з некоректними типами, від'ємними числовими значеннями або довжиною, що перевищує граничні значення, відхиляються глобальним `ValidationPipe`. П'ятий випадок підтверджує наявність шифрованого каналу між серверним застосунком і базою даних Supabase через SSL-з'єднання, налаштоване параметром `ssl: { rejectUnauthorized: false }` у конфігурації TypeORM.

4.4.3. Результати функціонального тестування
Загалом виконано 22 функціональних тестових випадки. Успішно пройдено 20 тестів з першої спроби, що становить приблизно 91 відсоток. Під час перевірок виявлено три дефекти різних рівнів критичності, які проаналізовано та усунуто.
Перший дефект середньої критичності виявлено в модулі активного тренування. При швидкому послідовному натисканні кнопки «Додати підхід» на клієнті виникала гонка станів у `ActiveWorkoutContext`, через що два нові підходи отримували однакове значення поля `order`, а наступне збереження на сервері відхиляло один з них через порушення обмеження унікальності. Проблему усунуто переходом на функціональну форму оновлення стану `setState((prev) => ...)`, яка гарантує читання найсвіжішого попереднього стану навіть при кількох викликах поспіль. Після виправлення дефект відтворити не вдалося.
Другий дефект, серйозної критичності, виявлено в логіці виявлення особистих рекордів. При видаленні підходу, який раніше встановив особистий рекорд, прапорець `isPR` зберігався на іншому підході, який фактично вже не був рекордним. Корінь проблеми полягав у тому, що метод `checkAndUpdateRecords` лише додавав нові записи, але не очищав застарілі. Виправлення впроваджено через попередній повний скид усіх записів `UserExerciseRecord` для конкретної вправи перед їх перерахунком на основі поточного набору підходів.
Третій дефект мінорної критичності виявлено в активації плану харчування. У випадку, коли користувач уже мав запис `UserMealPlan` для нового плану (наприклад, активував його у минулому, а пізніше деактивував), повторна активація залишала запис попереднього активного плану зі значенням `isActive = true`. Виправлення реалізовано двокроковою операцією: спочатку масове встановлення `isActive = false` для всіх записів користувача, а потім оновлення або створення запису для обраного плану.
Після усунення всіх трьох дефектів проведено регресійне тестування шляхом повторного виконання повного набору з 22 тестових випадків. Усі тести успішно пройдено, нових дефектів не виявлено.

4.4.4. Результати GUI тестування
За результатами тестування графічного інтерфейсу успішно пройдено вісім з дев'яти категорій перевірок. Виявлено два візуальні дефекти, які усунуто на етапі тестування.
Перший дефект полягав у недостатній контрастності світло-сірого тексту допоміжних підписів (поле `textMuted = #666666`) на темному фоні екрана `#0A0906`. Перевірка інструментом перевірки контрасту показала значення близько 3,4:1, що не задовольняє вимоги стандарту WCAG AA для звичайного тексту (мінімум 4,5:1). Виправлення виконано шляхом освітлення кольору до значення, що забезпечує контрастність не менш ніж 4,7:1 на основному тлі. Другий дефект стосувався поведінки екранної клавіатури iOS: при відкритті форми додавання продукту до прийому їжі клавіатура перекривала поле введення кількості. Усунуто додаванням компонента `KeyboardAvoidingView` з режимом `padding` навколо модального вмісту, що автоматично зміщує його при появі клавіатури.
Після усунення обох дефектів проведено регресійне тестування на трьох роздільних здатностях екранів (5,4″, 6,1″, 6,7″) на двох платформах. Усі категорії перевірок пройшли без зауважень, що демонструє стабільність відображення інтерфейсу. Окремий скріншот успішного проходження сценарію реєстрації та входу наведено на рис. 4.10.

Рис. 4.10. Скріншот результату успішного інтеграційного сценарію автентифікації

4.4.5. Результати інтеграційного тестування та безпеки
Усі вісім інтеграційних сценаріїв повного шляху виконано успішно. Перевірено, що клієнт коректно встановлює та використовує JWT-токен, серверний застосунок належно обчислює та зберігає особисті рекорди, синхронізація стану харчування між сесіями виконується без втрати записів, активація плану харчування атомарно деактивує попередній. Соціальні сценарії показали, що видимість шаблонів та тренувань іншого користувача коректно обмежується рівнем дружби: публічні елементи доступні усім, з обмеженням для друзів – лише після прийняття заявки. Перерахунок щоденного зведення після видалення прийому виконується миттєво за рахунок інвалідації кешу TanStack Query. Автоматичне вилогування користувача після отримання відповіді 401 спрацьовує без додаткових дій з боку інтерфейсу.
Усі п'ять тестових випадків з тестування безпеки пройдено успішно. У базі даних не виявлено жодного запису з паролем у відкритому вигляді. Спроби надіслати запити з підробленим токеном, без токена або з простроченим токеном відхиляються з кодом 401. Спроби доступу до даних чужого користувача стабільно повертають 403 або 404 залежно від того, чи перевіряється приналежність ресурсу до перевірки існування. Глобальний `ValidationPipe` коректно відхиляє некоректні DTO з повідомленням, що описує конкретне порушене обмеження. SSL-канал до Supabase підтверджено перевіркою параметрів з'єднання у конфігурації TypeORM. Тестування інтеграції та безпеки визнано повністю успішним.
Покриття функціональних вимог тестами становить 100 відсотків: кожна сформульована у Розділі 2 функціональна вимога перевіряється щонайменше одним функціональним та одним GUI-тестовим випадком. Покриття коду серверних модулів автоматизованими unit-тестами через інструмент Jest складає 64 відсотки за результатом запуску команди `npm run test:cov`, з найвищим показником у модулях каталогу вправ (понад 85 відсотків) та авторизації (близько 80 відсотків). Повний звіт з переліком пройдених тестових випадків та виявлених дефектів наведено в додатку Л.

4.5. Висновки до розділу
У цьому розділі описано програмну реалізацію спроєктованих у Розділі 3 компонентів мобільного застосунку Athlo та результати їх комплексного тестування. Серверну частину реалізовано на платформі Node.js фреймворком NestJS 11 за тришаровою схемою «контролер – сервіс – репозиторій» із чітким поділом на чотири доменних модулі. Доступ до даних інкапсульовано у репозиторії TypeORM, які працюють з керованою базою PostgreSQL у середовищі Supabase через SSL-канал. Авторизація реалізована на основі JSON Web Token із застосуванням бібліотеки Passport.js та bcrypt-хешування паролів, а декларативна валідація DTO забезпечена бібліотекою class-validator.
Клієнтську частину реалізовано на React Native 0.83.2 з Expo SDK 55 та маршрутизацією через Expo Router за файловою конвенцією. Серверний стан управляється бібліотекою TanStack Query, локальний – через контексти React, а взаємодія з API – через єдиний екземпляр Axios із перехоплювачами авторизації та обробкою помилки 401. Дизайн-система побудована навколо темної теми з зеленим акцентом, побудова графіків забезпечена бібліотекою react-native-gifted-charts. Спільний пакет типів `@athlo/shared` гарантує синхронізацію контрактів обміну даними між клієнтом і сервером.
Розроблено та виконано 22 функціональні тестові випадки, дев'ять категорій GUI-перевірок, вісім інтеграційних сценаріїв повного шляху та п'ять тестів безпеки. Функціональне тестування пройшли 91 відсоток випадків з першої спроби, GUI-тестування – близько 89 відсотків, інтеграційні тести та тести безпеки – 100 відсотків. Виявлено п'ять дефектів різного рівня критичності, для кожного запропоновано та реалізовано стратегію усунення. Після регресійного тестування нових дефектів не виявлено, що підтверджує стабільність розробленого програмного забезпечення та його готовність до пілотного використання серед цільової аудиторії.
