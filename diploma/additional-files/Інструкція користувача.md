Додаток М. Інструкція користувача

Цей документ призначений для кінцевих користувачів мобільного застосунку Athlo, а також для технічних спеціалістів, які виконують розгортання серверної інфраструктури та збірку клієнтського застосунку. Інструкція охоплює перелік компонентів системи, варіанти встановлення та запуску, обов'язкове налаштування середовища, основні сценарії використання та аналіз типових проблем, що можуть виникнути під час експлуатації.

М.1. Компоненти ПЗ
Програмний комплекс Athlo реалізований за клієнт-серверною архітектурою і складається з трьох основних рівнів: мобільного клієнта на платформах iOS та Android, серверного застосунку на платформі Node.js та реляційної бази даних PostgreSQL. Додатково використовується спільна бібліотека типів, що забезпечує єдиний контракт обміну даними між клієнтом та сервером. Перелік компонентів та середовищ їх виконання наведено в табл. М.1.

| Компонент | Призначення | Середовище виконання |
| --- | --- | --- |
| Мобільний клієнт (React Native / Expo) | Інтерфейс користувача, локальне зберігання токена автентифікації, взаємодія з REST API | iOS 14.0+, Android 8.0+ (API 26+) |

Рекомендовані вимоги до клієнтського пристрою: оперативна пам'ять – не менше 3 гігабайт; вільний дисковий простір – не менше 150 мегабайт; стабільне підключення до мережі Інтернет через Wi-Fi або мобільну мережу передачі даних. Рекомендовані вимоги до робочої станції розробника: операційна система Windows 10/11, macOS 12+ або Linux; встановлений Node.js версії 18 або новішої; встановлений Docker Desktop версії 4.0+ (для контейнерного варіанту розгортання); встановлений Git клієнт. Для збірки мобільного клієнта додатково потрібен встановлений Expo CLI або обліковий запис у сервісі Expo Application Services. Перелік допоміжних конфігураційних файлів наведено в табл. М.2.

М.2. Встановлення ПЗ
Розгортання системи виконується незалежно для трьох частин: серверного застосунку, бази даних та мобільного клієнта. Для кожної з частин підтримується декілька варіантів встановлення, що дозволяє підібрати найзручніший спосіб залежно від поставленої мети – локальна розробка, тестове середовище або промислове розгортання.

М.2.1. Розгортання серверної частини
Підтримуються три варіанти запуску серверного застосунку: у Docker-контейнері (з автоматичною побудовою образу), безпосередньо на робочій машині розробника командою `npm run start:dev`, або у хмарному середовищі Render.

Варіант 1 – запуск у Docker-контейнері. Цей спосіб є рекомендованим для локальної розробки та тестування, оскільки повністю ізолює середовище виконання та не потребує локальної інсталяції Node.js. У корені репозиторію наявний файл `docker-compose.yml`, який описує два сервіси – `postgres` (база даних) та `api` (серверний застосунок). Порядок дій наведено нижче.
1. Встановити Docker Desktop версії 4.0 або новішої та переконатись, що сервіс запущений командою `docker info`.
2. Клонувати репозиторій проєкту у робочу директорію командою `git clone <repository-url> athlo`.
3. Перейти до кореневої директорії проєкту та, за потреби, створити файл `.env` з власним значенням змінної `JWT_SECRET` (інакше буде використано значення за замовчуванням з `docker-compose.yml`).
4. Виконати побудову та запуск контейнерів командою `docker compose up --build -d`.
5. Дочекатись завершення ініціалізації PostgreSQL (приблизно 15–20 секунд) та переконатись у працездатності API через виклик ендпоінта документації за адресою `http://localhost:4000/api/docs`.
6. Запустити міграції бази даних у запущеному контейнері командою `docker compose exec api npx typeorm-ts-node-commonjs migration:run -d src/config/data-source.ts`.

Зупинка контейнерів виконується командою `docker compose down`; для повного очищення збережених даних бази – командою `docker compose down --volumes`.

Варіант 2 – локальний запуск без Docker. Цей спосіб підходить, якщо розробник вже має встановлений Node.js та локальний або хмарний екземпляр PostgreSQL і хоче працювати безпосередньо із вихідним кодом, користуючись гарячим перезавантаженням. Порядок дій наведено нижче.
1. Клонувати репозиторій проєкту командою `git clone <repository-url> athlo`.
2. У кореневій директорії проєкту встановити всі залежності монорепозиторію командою `npm install`. Менеджер npm автоматично виконає збірку спільного пакета `@athlo/shared`.
3. Створити файл `apps/api/.env` за прикладом `apps/api/.env.example`. Вказати у змінній `DATABASE_URL` рядок підключення до наявної бази PostgreSQL, у змінній `JWT_SECRET` – довільний рядок не менше 32 символів. Для бази без SSL встановити `DATABASE_SSL=false`.
4. Запустити міграції командою `npm run migration:run --workspace=apps/api`.
5. Запустити сервер у режимі розробки командою `npm run start:dev --workspace=apps/api`. Сервер прийматиме запити на порту, вказаному у `PORT` (за замовчуванням 4000), та автоматично перезавантажуватиметься при зміні вихідного коду.

Варіант 3 – розгортання на хмарній платформі Render. Цей спосіб використовується для публічно доступного промислового екземпляра застосунку. Порядок дій наведено нижче.
1. Створити обліковий запис у сервісі Render (render.com) та підключити репозиторій з вихідним кодом через GitHub-інтеграцію.
2. Створити новий сервіс типу «Web Service», вказати галузь репозиторію (за замовчуванням `main`), кореневий каталог – `apps/api`, команду збірки – `npm install && npm run build`, команду запуску – `npm run start:prod`.
3. У розділі «Environment» додати змінні середовища `DATABASE_URL`, `JWT_SECRET` та `DATABASE_SSL=true` (для з'єднання з Supabase або іншою керованою базою).
4. Запустити перше розгортання кнопкою «Deploy». При кожному наступному push-commit у відстежувану галузь Render автоматично виконає перебудову та перезапуск сервісу.
5. Після успішного розгортання отримати публічну адресу сервера (формат `https://athlo-api.onrender.com`) та використовувати її у клієнтському застосунку.

М.2.2. Розгортання бази даних
Підтримуються два варіанти зберігання даних: локальний PostgreSQL у Docker-контейнері та керований хмарний сервіс Supabase.

Варіант 1 – PostgreSQL у Docker-контейнері. Цей спосіб є складовою частиною описаного у пункті М.2.1 файлу `docker-compose.yml`. У ньому використовується офіційний образ `postgres:16-alpine`, дані зберігаються у іменованому Docker-томі `athlo-postgres-data`, що зберігає вміст бази між перезапусками контейнера. Якщо потрібно лише підняти базу даних без серверного застосунку, виконується команда `docker compose up postgres -d`. Підключення до бази здійснюється за рядком `postgresql://athlo:athlo@localhost:5432/athlo`. Для цього варіанту в серверному застосунку обов'язково встановлюється змінна `DATABASE_SSL=false`, оскільки локальний PostgreSQL не підтримує SSL-з'єднання за замовчуванням.

Варіант 2 – керований сервіс Supabase. Цей спосіб є рекомендованим для промислового середовища, оскільки забезпечує автоматичне резервне копіювання, пулінг з'єднань та шифрований канал зв'язку. Порядок дій наведено нижче.
1. Створити обліковий запис у сервісі Supabase (supabase.com) та новий проєкт із вказанням регіону розміщення.
2. У розділі «Project Settings» – «Database» отримати рядок підключення формату `postgresql://postgres:<password>@<host>:5432/postgres` (рекомендується використовувати підключення «Session pooler» для серверного застосунку).
3. Скопіювати рядок підключення у змінну `DATABASE_URL` середовища API; залишити `DATABASE_SSL=true` або не вказувати її взагалі.
4. Виконати міграції згідно з обраним способом розгортання API.

М.2.3. Комбінації варіантів розгортання
Описані варіанти можна довільно комбінувати залежно від мети. Найпоширеніші конфігурації наведено в табл. М.3.

Таблиця М.3
Комбінації варіантів розгортання серверної частини та бази даних

| Конфігурація | Сервер | База даних | Призначення |
| --- | --- | --- | --- |
| Повна локальна | Docker або `npm run start:dev` | PostgreSQL у Docker | Розробка та автономне тестування без зовнішніх залежностей |
| Локальний сервер + хмарна БД | `npm run start:dev` | Supabase | Розробка з реальними виробничими даними |
| Промислова | Render | Supabase | Публічно доступний екземпляр для пілотного використання |
| Гібридна | Render | PostgreSQL у Docker (на VPS) | Самостійний хостинг бази при використанні хмарного сервера |

М.2.4. Встановлення мобільного клієнта
Підтримуються три варіанти запуску мобільного клієнта: через сервіс Expo Application Services з готовою збіркою, через застосунок Expo Go для швидкого попереднього перегляду, та через нативні інструменти Android Studio або Xcode для повноцінної розробки.

Варіант 1 – збірка через Expo Application Services (EAS). Цей варіант використовується для розповсюдження готового застосунку серед тестувальників та публікації у магазинах застосунків. Він не вимагає від кінцевого користувача встановлення Node.js чи інших засобів розробки. У файлі `eas.json` визначено три профілі збірки: `development` (з підтримкою інструментів розробника), `preview` (внутрішнє розповсюдження APK для Android) та `production` (фінальна збірка для магазинів). Порядок дій для розробника наведено нижче.
1. Встановити EAS CLI глобально командою `npm install -g eas-cli` та виконати вхід у обліковий запис Expo командою `eas login`.
2. Перейти до директорії `apps/mobile` та запустити збірку відповідного профілю: для тестового APK – `eas build --profile preview --platform android`; для тестового збору iOS у TestFlight – `eas build --profile preview --platform ios`; для фінальних збірок – `eas build --profile production --platform <android|ios>`.
3. Дочекатись завершення збірки у хмарному середовищі EAS (зазвичай 10–20 хвилин) та отримати посилання на готовий артефакт.
4. Поширити посилання на APK-файл серед користувачів Android або надіслати запрошення у TestFlight для користувачів iOS.

Порядок встановлення для кінцевого користувача на пристроях Android: відкрити отримане посилання у браузері, завантажити APK-файл, перейти до налаштувань пристрою та у розділі «Безпека» дозволити встановлення з невідомих джерел, відкрити завантажений файл і підтвердити встановлення. Для пристроїв iOS: встановити застосунок TestFlight з App Store, відкрити отримане запрошення, прийняти його та натиснути «Встановити».

Варіант 2 – запуск через Expo Go. Цей варіант призначений для швидкого попереднього перегляду застосунку без створення повноцінної збірки і є найзручнішим способом демонстрації. Порядок дій наведено нижче.
1. Встановити застосунок Expo Go з Google Play (Android) або App Store (iOS) на цільовий мобільний пристрій.
2. На робочій машині виконати `npm install` у корені репозиторію.
3. Запустити сервер розробки командою `npm run start --workspace=apps/mobile` (або `npx expo start` у директорії `apps/mobile`).
4. У термінал виведеться QR-код. Просканувати його камерою на iOS або через сам застосунок Expo Go на Android. Мобільний пристрій повинен знаходитись у тій самій локальній мережі, що й робоча машина.
5. Expo Go автоматично завантажить JavaScript-бандл та відобразить інтерфейс застосунку. Будь-яка зміна вихідного коду спричинить миттєве оновлення інтерфейсу.

Варіант 3 – локальна збірка через Android Studio або Xcode. Цей варіант надає повний доступ до нативних можливостей платформи (нативні модулі, дебагер, симулятори) і використовується, коли стандартних можливостей Expo Go недостатньо. Порядок дій для Android наведено нижче.
1. Встановити Android Studio та налаштувати Android SDK (мінімальна версія API 26).
2. Створити віртуальний пристрій Android Virtual Device або підключити фізичний пристрій з увімкненим режимом розробника та налагодженням USB.
3. У директорії `apps/mobile` виконати команду `npx expo run:android`. Expo автоматично згенерує нативний проєкт, відкриє Android Studio, виконає збірку та встановить застосунок на обраний пристрій.

Порядок дій для iOS наведено нижче.
1. Встановити Xcode 15+ на пристрої під управлінням macOS.
2. У директорії `apps/mobile` виконати команду `npx expo run:ios`. Expo автоматично згенерує iOS-проєкт, відкриє Xcode та запустить застосунок у обраному симуляторі.

М.3. Налаштування ПЗ
Налаштування серверної частини виконується через файл змінних середовища `apps/api/.env`, без коректно заповненого якого серверний застосунок не запуститься. Перелік обов'язкових та опціональних змінних наведено в табл. М.4.

Таблиця М.4
Змінні середовища серверного застосунку

| Змінна | Призначення | Приклад значення |
| --- | --- | --- |
| DATABASE_URL | Рядок підключення до PostgreSQL у форматі `postgresql://user:password@host:port/database` | postgresql://athlo:athlo@localhost:5432/athlo |
| DATABASE_SSL | Прапорець SSL-з'єднання; для локальної бази без SSL – «false», для Supabase – «true» або відсутня | false |
| JWT_SECRET | Криптографічний ключ для підпису JWT-токенів автентифікації (рекомендована довжина – від 32 символів) | a7f3...довгий випадковий рядок |
| PORT | Порт, на якому серверний застосунок прийматиме HTTP-запити | 4000 |

Налаштування адреси API у мобільному клієнті виконується автоматично через файл `apps/mobile/api/config.ts`. У режимі розробки (`__DEV__`) клієнт визначає адресу робочої машини з параметрів Expo та підключається до неї за портом 4000. У виробничій збірці використовується константа `PRODUCTION_API_URL`, значення якої необхідно змінити на адресу розгорнутого екземпляра сервера, якщо вона відрізняється від `https://athlo-api.onrender.com`.

Налаштування облікового запису кінцевого користувача виконується безпосередньо у застосунку. Після першого входу користувач переходить на вкладку «Profile» та через кнопки «Edit Profile» і «Settings» налаштовує особисті дані: повне ім'я, нікнейм, добову ціль споживання води (поле «Water Goal»), систему одиниць виміру, налаштування сповіщень та тему оформлення. У розділі «Body Metrics» доступне додавання записів антропометричних показників – маси тіла, відсотка жиру, окружностей – які використовуватимуться для побудови графіків динаміки.

М.4. Базові функції ПЗ
Інтерфейс клієнтського застосунку побудований навколо трьох основних вкладок, доступних через нижню навігаційну панель: «Nutrition» (харчування), «Workouts» (тренування) та «Profile» (профіль). Кожна вкладка містить набір вкладених екранів, доступ до яких здійснюється через кнопки навігації або модальні листи. Опис основних сценаріїв роботи наведено нижче.

М.4.1. Автентифікація та реєстрація
При першому запуску застосунку відображається стартовий екран входу. Для створення облікового запису необхідно перейти на екран «Sign Up» та заповнити форму: електронна адреса, повне ім'я, нікнейм та пароль (мінімум 8 символів). Після надсилання форми сервер виконує валідацію даних, перевіряє унікальність електронної адреси та нікнейма, створює запис у базі та повертає JWT-токен. Токен зберігається у захищеному сховищі `expo-secure-store` і використовується для всіх наступних запитів. Для повторного входу достатньо ввести електронну адресу та пароль на екрані «Sign In». Завершення сеансу виконується через кнопку «Logout» у налаштуваннях профілю; повне видалення облікового запису – через кнопку «Delete Account» у тому самому розділі.

М.4.2. Логування тренування
Вкладка «Workouts» відкривається на головному екрані тренувального розділу, який містить дві швидкі дії – «Empty Workout» (нове порожнє тренування) і «From Template» (старт із наявного шаблону) – а також горизонтальний список власних шаблонів та вертикальну стрічку «Recent Workouts» з історією завершених тренувань. Натискання кнопки «Empty Workout» створює нову сесію без попередньо визначених вправ; натискання картки шаблону у списку «My Templates» або кнопки «From Template» з подальшим вибором шаблону створює сесію з автоматично заповненою структурою. Після створення сесії застосунок переходить на екран «Active Workout», де у верхній частині відображається статистична панель з лічильником загального обсягу піднятої ваги, кількістю виконаних та запланованих підходів, а також часом тренування з моменту запуску.
Кнопка «+ Add Exercise» відкриває екран «Exercise Picker» з повним каталогом вправ та фільтрами за м'язовою групою, обладнанням і пошуком за назвою. Після вибору вправа додається до сесії у вигляді розгорнутої картки з таблицею підходів. Поля таблиці визначаються типом відстеження вправи: для силових вправ – вага та повторення; для вправ з власною вагою – лише повторення; для кардіо-вправ – тривалість та опціональна дистанція. Поряд із полями введення сірим кольором відображається підказка з показниками останнього виконання тієї самої вправи. Натискання чекбокса навпроти підходу зберігає його на сервері та автоматично перевіряє, чи встановлено новий особистий рекорд; у випадку встановлення відображається сповіщення «AchievementToast». Після завершення підходу автоматично запускається таймер відпочинку, якщо у вправі вказано відповідне значення часу.
Кнопка «Finish» відкриває екран «Finish Workout», на якому опціонально вводиться суб'єктивна оцінка навантаження (RPE) та коментар. Підтвердження завершення фіксує час закінчення сесії, запускає перевірку розблокування глобальних досягнень (загальна кількість тренувань, підходів, піднятої ваги, сумарного часу) та переадресовує на екран «Workout Summary» з підсумками. Якщо під час активного тренування користувач переходить на інші вкладки, у нижній частині екрана відображається міні-панель «FloatingWorkoutMini» з пропозицією повернутись до сесії.

М.4.3. Управління шаблонами тренувань
Перехід на екран «Templates» відкриває розділ з трьома вкладками: «My» (власні шаблони), «Public» (публічно доступні шаблони усіх користувачів) та «Friends» (шаблони друзів з відповідним рівнем видимості). Створення нового шаблону виконується кнопкою «+ New» з відкриттям форми, у якій вказуються назва, опис та рівень видимості: «Private» (приватний), «Friends» (лише для друзів) або «Public» (загальнодоступний). Після створення шаблон відкривається на окремому екрані, де додаються вправи з каталогу, для кожної визначається порядок виконання, орієнтовний час відпочинку між підходами та цільові параметри підходів. Збережений шаблон стає доступним для повторного запуску через головний екран тренувань. Публічні шаблони інших користувачів можна зберегти у власну колекцію кнопкою «Save».

М.4.4. Журнал харчування
Вкладка «Nutrition» відкривається на головному екрані харчового розділу. У верхній частині розміщена смуга навігації по датах із стрілками «вперед/назад» та можливістю вибору довільної дати через календарний пікер. Нижче, за наявності активного плану, відображається банер «ActivePlanBanner» з його назвою та переходом до перегляду повного плану. Блок «Daily Macros Summary» візуалізує сумарну калорійність та споживання білків, жирів і вуглеводів за обраний день у вигляді чотирьох індикаторів. Під ним розміщений перемикач режимів «Meals» / «Water».
У режимі «Meals» доступний горизонтальний рядок чипів типів прийому їжі (сніданок, обід, вечеря, перекус) для фільтрації списку. Кнопка «+ Add Meal» відкриває модальний лист «MealFormSheet» з вибором типу прийому, опціональною назвою, часом споживання та можливістю одразу додати позиції. Кожен збережений прийом відображається у вигляді картки «MealCard» зі списком позицій та сумарними макронутрієнтами. Кнопка «+ Add Food» у межах картки відкриває екран «Food Picker» з пошуковим полем по системній та користувацькій базі продуктів. Після вибору продукту необхідно вказати кількість та одиницю виміру з випадаючого списку (грами, мілілітри, штуки, скибки тощо); калорійність та макронутрієнти автоматично перераховуються через коефіцієнт `conversionFactor`. У випадку відсутності продукту в базах доступна кнопка створення нового запису з ручним введенням харчової цінності на 100 грамів. Натискання на позицію відкриває «MealItemActionSheet» з можливостями зміни кількості, заміни на інший продукт або видалення.
У режимі «Water» відображається компонент «WaterTracker» з поточним обсягом спожитої води відносно цілі, кнопками швидкого запису типових об'ємів (200, 300, 500 мл) та полем для довільного значення. Перехід до екрана «Meal Plans» через кнопку у заголовку відкриває список багатоденних планів харчування з можливостями створення нового плану, перегляду структури днів та активації плану. Активація автоматично деактивує попередній активний план, забезпечуючи унікальність активного плану на користувача. Екран «Nutrition History» надає можливість переглянути зведення харчування за минулі періоди.

М.4.5. Профіль, статистика та досягнення
Вкладка «Profile» містить картку з аватаром, нікнеймом, повним ім'ям та лічильниками тренувань і друзів. Нижче розміщений блок «BarChartBlock» з графіком продуктивності, який підтримує перемикання періоду (тиждень, місяць, рік) та метрики (загальний обсяг, кількість підходів, тривалість тощо). Чотири карти «NavCard» забезпечують перехід до спеціалізованих розділів аналітики:
- «Calendar» – календарна сітка з виділеними днями тренувань.
- «Metrics» (Body Metrics) – журнал антропометричних вимірювань з лінійними графіками динаміки кожного показника.
- «Exercise Progress» – детальна аналітика по окремих вправах з графіком найкращих результатів у часі.
- «Achievements» – перелік досягнень з двома вкладками: розблоковані та заблоковані з індикатором прогресу.

Управління особистими даними виконується через кнопки у верхній частині профілю: «Edit Profile» (іконка олівця) відкриває форму зміни імені та нікнейма, «Settings» (іконка шестерні) – екран загальних налаштувань з полями цілі по воді, системи одиниць, налаштувань сповіщень та теми, а також кнопками виходу та видалення облікового запису.

М.4.6. Соціальний модуль
Перехід до екрана «Friends» виконується через лічильник друзів на картці профілю або через відповідний розділ налаштувань. Екран містить три вкладки: «Friends» (поточні друзі), «Requests» (вхідні та вихідні запити) та «Find» (пошук користувачів за нікнеймом). На вкладці «Find» введення нікнейма у пошукове поле формує перелік знайдених користувачів з кнопкою «Add»; натискання надсилає запит зі статусом «pending». На вкладці «Requests» відображаються отримані запити з кнопками «Accept» та «Reject», а також надіслані запити з кнопкою «Cancel». Натискання картки користувача у будь-якому списку відкриває профіль іншого користувача на екрані `[userId]`, де доступні його публічні шаблони та шаблони з рівнем видимості «Friends» (у разі підтвердженого зв'язку).

М.5. Аналіз можливих помилок
Помилки під час експлуатації застосунку поділяються на три категорії: проблеми клієнт-серверної взаємодії, помилки бізнес-логіки специфічні для домену та проблеми, що виникають при розгортанні. Перелік типових проблем та шляхів їх усунення наведено в табл. М.5.

Таблиця М.5
Усунення типових несправностей

| Опис проблеми | Можлива причина | Шлях розв'язання |
| --- | --- | --- |

Першим кроком у діагностиці будь-якої помилки клієнт-серверної взаємодії є перевірка стану серверного контейнера командою `docker compose ps` (для локального розгортання) або перегляд статусу сервісу на платформі Render. Журнал серверного застосунку переглядається командою `docker compose logs api -f` або через відповідний розділ панелі управління хмарної платформи. Інтерактивна документація API за адресою `/api/docs` дозволяє перевірити доступність конкретних маршрутів та коректність токенів автентифікації.
