Додаток М. Інструкція користувача

Цей документ призначений для кінцевих користувачів мобільного застосунку Athlo, а також для технічних спеціалістів, які виконують розгортання серверної інфраструктури та збірку клієнтського застосунку. Інструкція охоплює перелік компонентів системи, варіанти встановлення та запуску, обов'язкове налаштування середовища, основні сценарії використання та аналіз типових проблем, що можуть виникнути під час експлуатації.

М.1. Компоненти ПЗ
Програмний комплекс Athlo реалізований за клієнт-серверною архітектурою і складається з трьох основних рівнів: мобільного клієнта на платформах iOS та Android, серверного застосунку на платформі Node.js та реляційної бази даних PostgreSQL.
Рекомендовані вимоги до клієнтського пристрою: оперативна пам'ять – не менше 3 гігабайт; вільний дисковий простір – не менше 150 мегабайт; стабільне підключення до мережі Інтернет через Wi-Fi або мобільну мережу передачі даних. Рекомендовані вимоги до робочої станції розробника: операційна система Windows 10/11, macOS 12+ або Linux; встановлений Node.js версії 18 або новішої; встановлений Docker Desktop версії 4.0+ (для контейнерного варіанту розгортання); встановлений Git клієнт. Для збірки мобільного клієнта додатково потрібен встановлений Expo CLI або обліковий запис у сервісі Expo Application Services. Перелік допоміжних конфігураційних файлів наведено в табл. М.1.

М.2. Встановлення ПЗ
Розгортання системи виконується незалежно для трьох частин: серверного застосунку, бази даних та мобільного клієнта. Для кожної з частин підтримується декілька варіантів встановлення, що дозволяє підібрати найзручніший спосіб залежно від поставленої мети – локальна розробка, тестове середовище або промислове розгортання.

М.2.1. Розгортання бази даних
Підтримуються два варіанти зберігання даних: локальний PostgreSQL у Docker-контейнері та керований хмарний сервіс Supabase.

Варіант 1 – PostgreSQL у Docker-контейнері. База даних може бути розгорнута автоматично разом із серверним застосунком через файл docker-compose.yml (див. п. М.2.2). Дані зберігаються у томі athlo-postgres-data. Автономний запуск бази (без серверної частини) виконується командою docker compose up postgres -d, після чого запускається скрипт створення необхідної структури. Рядок підключення для локального розгортання: postgresql://athlo:athlo@localhost:5432/athlo (для сервера обов'язково встановити DATABASE_SSL=false).

Варіант 2 – керований сервіс Supabase. Рекомендовано для промислового середовища. Порядок дій:
1. Створити проєкт у сервісі Supabase.
2. Отримати рядок підключення у розділі «Project Settings» – «Database».
3. Зберегти отриманий рядок для налаштування змінної DATABASE_URL серверного застосунку (змінну DATABASE_SSL необхідно встановити як true).

М.2.2. Розгортання серверної частини
Підтримуються два варіанти запуску серверного застосунку: у Docker-контейнері (з автоматичною побудовою образу) або у хмарному середовищі Render.

Варіант 1 – запуск у Docker-контейнері. Рекомендовано для локальної розробки. Цей спосіб одночасно запускає і базу даних (з Варіанту 1 вище), і серверний застосунок. Порядок дій:
1. Встановити Docker Desktop (версії 4.0+) та переконатись, що сервіс запущений.
2. Клонувати репозиторій командою git clone <repository-url> athlo та перейти у створену директорію.
3. Створити файл .env з власним значенням JWT_SECRET (за потреби).
4. Виконати запуск контейнерів командою docker compose up --build -d.
5. Дочекатись ініціалізації БД та переконатись у працездатності API за адресою http://localhost:4000/api/docs.

Зупинка контейнерів виконується командою docker compose down; очищення збережених даних – docker compose down --volumes.

Варіант 2 – розгортання на хмарній платформі Render. Використовується для промислового екземпляра застосунку. Порядок дій:
1. Створити обліковий запис на Render та підключити репозиторій через GitHub.
2. Створити «Web Service», вказавши кореневий каталог (apps/api), команду збірки (npm install && npm run build) та запуску (npm run start:prod).
3. У розділі «Environment» додати змінні: DATABASE_URL (вказати збережений рядок підключення до БД, наприклад, з Supabase), JWT_SECRET та DATABASE_SSL=true.
4. Натиснути «Deploy». Кожен наступний push-commit ініціюватиме авторозгортання. Після розгортання виконати міграції бази даних.

М.2.3. Комбінації варіантів розгортання
Описані варіанти можна довільно комбінувати залежно від мети.

М.2.4. Встановлення мобільного клієнта
Підтримуються два варіанти запуску мобільного клієнта: через сервіс Expo Application Services (EAS) та через нативні інструменти (Android Studio / Xcode).. Перед створенням виробничої збірки необхідно переконатись, що у файлі apps/mobile/api/config.ts вказана правильна адреса розгорнутого сервера у константі PRODUCTION_API_URL.

Варіант 1 – збірка через Expo Application Services (EAS). Цей варіант використовується для розповсюдження готового застосунку.
1. Встановити EAS CLI глобально командою npm install -g eas-cli та виконати вхід у обліковий запис Expo командою eas login.
2. Перейти до директорії apps/mobile та запустити збірку відповідного профілю: для тестового APK – eas build --profile preview --platform android; для тестового збору iOS у TestFlight – eas build --profile preview --platform ios; для фінальних збірок – eas build --profile production --platform <android|ios>.
3. Після завершення збірки у хмарному середовищі EAS отримати посилання на готовий артефакт.
4. Для Android: завантажити APK та дозволити встановлення з невідомих джерел. Для iOS: використати TestFlight.  

Варіант 2 – локальна збірка через Android Studio або Xcode. Цей варіант надає повний доступ до нативних можливостей платформи (нативні модулі, дебагер, симулятори) і використовується для розробки. Порядок дій для Android наведено нижче.
1. Встановити Android Studio та налаштувати Android SDK (мінімальна версія API 26).
2. Створити віртуальний пристрій Android Virtual Device або підключити фізичний пристрій з увімкненим режимом розробника та налагодженням USB.
3. У директорії apps/mobile виконати команду npx expo run:android. Expo автоматично згенерує нативний проєкт, відкриє Android Studio, виконає збірку та встановить застосунок на обраний пристрій.

Порядок дій для iOS наведено нижче.
1. Встановити Xcode 15+ на пристрої під управлінням macOS.
2. У директорії apps/mobile виконати команду npx expo run:ios. Expo автоматично згенерує iOS-проєкт, відкриє Xcode та запустить застосунок у обраному симуляторі.

М.3. Налаштування ПЗ
Після успішного встановлення та запуску додаткових налаштувань системи не передбачено. Всі необхідні параметри задаються на етапі розгортання.

М.4. Базові функції ПЗ
Система містить в собі велику кількість функцій, які доступні кожному користувачеві. Серед основного функціоналу є:

- Реєстрація та вхід. Для початку роботи необхідно створити акаунт на екрані «Sign Up» або увійти у наявний через екран «Sign In».
- Створення тренування. Користувач може розпочати порожнє тренування («Empty Workout») або обрати один зі створених шаблонів («From Template») на вкладці «Workouts».
- Логування вправ. Під час тренування можна додавати вправи з каталогу, вказувати вагу, кількість повторень чи час, а також відмічати їх виконання.
- Створення шаблонів тренувань. На екрані «Templates» можна створювати власні шаблони тренувань, встановлювати їх видимість (приватні, для друзів, публічні) та зберігати шаблони інших користувачів.
- Відстеження харчування. На вкладці «Nutrition» користувач може додавати прийоми їжі, шукати продукти в базі та вказувати їх кількість для автоматичного розрахунку калорій.
- Трекінг води. Також доступний лічильник спожитої води за день із зручними кнопками швидкого додавання.
- Перегляд статистики. У вкладці «Profile» користувач може аналізувати графіки своїх результатів, переглядати історію тренувань, динаміку ваги та отримані досягнення.
- Соціальна взаємодія. У розділі «Friends» можна шукати інших користувачів, надсилати запити на дружбу та переглядати їхні тренувальні шаблони.

М.5. Аналіз можливих помилок
Перелік типових проблем, які можуть виникнути під час розгортання та експлуатації застосунку, наведено в табл. М.3.

Таблиця М.3
Усунення типових несправностей

| Опис проблеми | Можлива причина | Шлях розв'язання |
| --- | --- | --- |
| Перший запит до сервера після тривалої паузи виконується 30–60 секунд | Безкоштовний тариф Render зупиняє контейнер після 15 хвилин неактивності; запит ініціює «cold start» | Дочекатись повного завантаження екрана; за критичності розгорнути сервер на платному тарифі або налаштувати періодичний пінг |
| Помилка SSL під час запуску міграцій локально проти Docker PostgreSQL | За замовчуванням TypeORM підключається з параметром SSL, який локальний контейнер не підтримує | Додати у apps/api/.env змінну DATABASE_SSL=false та повторити запуск міграцій |
| Після кількох днів неактивності користувач автоматично виходить з облікового запису | Термін дії JWT-токена обмежено сімома днями; перехоплювач відповіді 401 видаляє токен зі сховища | Увійти повторно у формі «Sign In»; буде отримано новий токен з оновленим терміном дії |

У разі виникнення непередбачуваних збоїв у роботі мобільного клієнта, які не описані в таблиці, доцільно перевірити стабільність інтернет-з'єднання та стан серверної інфраструктури за логами контейнера або панелі хмарного хостингу. Якщо збій повторюється і перешкоджає подальшій роботі, слід звернутися до розробника.
