РОЗДІЛ 3. АРХІТЕКТУРА ТА ПРОЄКТУВАННЯ СИСТЕМИ ПЕРСОНАЛЬНОГО ПЛАНУВАННЯ

3.1. Архітектурне рішення та компонентна структура системи
Для розроблення застосунку Athlo обрано клієнт-серверну архітектуру, яка забезпечує чіткий поділ між рівнем інтерфейсу користувача, рівнем бізнес-логіки та рівнем зберігання даних. Такий підхід дозволяє незалежно оновлювати кожен із компонентів, не порушуючи роботу решти системи. Оскільки застосунок розрахований на функціонування на двох мобільних платформах одночасно, клієнт-серверна модель є природним вибором: мобільний клієнт відповідає виключно за відображення даних та взаємодію з користувачем, тоді як уся логіка обробки зосереджена на сервері.
Клієнтську частину застосунку сплановано на базі фреймворку React Native разом із платформою Expo [15], яка розширює стандартне середовище React Native набором API-інтерфейсів та хмарними інструментами компіляції для платформ iOS і Android. Клієнт взаємодіє з сервером через REST API за протоколом HTTPS. Кожен запит до захищеного ресурсу містить у заголовку токен автентифікації формату JSON Web Token (JWT) [16], що дозволяє серверу без збереження стану сесій перевірити особу та повноваження запитувача.
Серверна частина побудована на фреймворку NestJS [13] для платформи Node.js, який запроваджує тришаровий підхід до організації коду. Перший шар – контролери – отримує HTTP-запити, виконує маршрутизацію та первинну валідацію вхідних даних. Другий шар – сервіси – містить основну бізнес-логіку: розрахунки калорійності, перевірку особистих рекордів, присвоєння досягнень. Третій шар – репозиторії – забезпечує взаємодію з базою даних через об'єктно-реляційне відображення за допомогою TypeORM [17]. Кожний шар залежить лише від інтерфейсів нижчого шару, що підвищує тестованість і спрощує заміну окремих компонентів.
Серверний застосунок поділено на чотири функціонально незалежні модулі, кожен із яких охоплює окремий домен системи. Модуль користувача відповідає за реєстрацію, автентифікацію, управління профілем, відстеження антропометричних показників та функції соціальної взаємодії між користувачами. Модуль каталогу вправ надає доступ до структурованої бібліотеки фізичних вправ, обладнання та м'язових груп із підтримкою користувацьких записів. Модуль тренувань реалізує відстеження тренувальних сесій, управління шаблонами тренувань, систему особистих рекордів, досягнень і статистики. Модуль харчування охоплює управління базою продуктів харчування, ведення журналу прийомів їжі, фіксацію споживання води та планування раціону.
Обраний підхід безпосередньо забезпечує реалізацію нефункціональних вимог, сформованих у розділі 2. Масштабованість досягається завдяки незалежності модулів один від одного: розширення функціональності в межах одного модуля не торкається інших. Безпека забезпечується на кількох рівнях: паролі зберігаються у хешованому вигляді з використанням алгоритму bcrypt, JWT-токени [16] обмежують доступ до захищених ресурсів, а кожна операція зміни або видалення запису супроводжується перевіркою належності ресурсу поточному користувачу. Зручність підтримки забезпечується дотриманням принципу розділення відповідальностей: кожен компонент відповідає за строго визначене коло завдань.
Логічна структура компонентів системи та зв'язки між ними представлені у вигляді діаграми компонентів у додатку В.

3.2. Інфраструктурне середовище розгортання
Фізична модель розгортання визначає, яким чином спроєктовані логічні компоненти розподіляються між апаратно-обчислювальними вузлами та мережевою інфраструктурою. Інфраструктура системи охоплює три фізичних рівні: мобільний пристрій кінцевого користувача, сервер застосунку та сервер бази даних.
Клієнтський рівень – це мобільний пристрій користувача під управлінням iOS або Android, на якому функціонує скомпільована збірка React Native / Expo [15]. Для збірки та розповсюдження застосунку використовується хмарний сервіс Expo Application Services (EAS) [18] – складова екосистеми Expo, що дозволяє компілювати нативні бінарні файли для iOS та Android у хмарному середовищі без потреби у локальному налаштуванні збірки, а також забезпечує механізм розповсюдження застосунку серед тестових пристроїв.
Рівень застосунку – це процес Node.js, у якому виконується серверний застосунок на базі NestJS. Сервер приймає вхідні HTTPS-запити від мобільних клієнтів, обробляє їх у відповідних сервісних модулях і повертає структуровані JSON-відповіді. Для хостингу серверного застосунку обрано хмарну платформу Render [19], яка підтримує автоматичне перерозгортання при кожному новому push-commit у репозиторій: зміни у вихідному коді одразу призводять до оновлення запущеного сервісу без ручних операцій.
Рівень даних представлений реляційною базою даних PostgreSQL [14] – відкритим програмним забезпеченням корпоративного класу, що вирізняється розвиненою підтримкою транзакцій за моделлю ACID, потужними механізмами індексування та широкими можливостями розширення типів даних. Для хостингу бази даних планується використання керованого хмарного сервісу Supabase [20], що надає PostgreSQL-інфраструктуру з вбудованим пулінгом з'єднань, автоматичним резервним копіюванням та SSL-захистом каналу зв'язку.
Вся комунікація між мобільним клієнтом та сервером застосунку здійснюється за протоколом HTTPS, що унеможливлює перехоплення даних під час передавання. База даних не має прямого зовнішнього доступу – запити до неї надходять виключно від серверного застосунку у межах захищеного мережевого сегменту.
Діаграма розгортання, що відображає розподіл системних компонентів між фізичними вузлами та мережеву топологію, наведена у додатку Г.
3.3. Моделювання ключових сценаріїв взаємодії
Для розуміння динамічної поведінки системи необхідно змоделювати основні бізнес-процеси та послідовності взаємодії між компонентами. Виявлено шість ключових процесів, що охоплюють усі основні функціональні характеристики застосунку: автентифікацію, проведення тренування, створення шаблону тренування, ведення журналу харчування, формування плану харчування та перегляд статистики.
Сценарій автентифікації розпочинається з переходу на екран входу. Новий користувач обирає реєстрацію, вводить електронну адресу, повне ім'я, нікнейм та пароль, після чого сервер виконує валідацію даних, перевіряє унікальність адреси та створює обліковий запис із хешованим паролем. При успішній реєстрації генерується JWT-токен [16] і користувач отримує доступ до застосунку. За наявності існуючого облікового запису користувач вводить адресу та пароль, сервер порівнює хеш і у разі збігу видає токен. Помилкові вхідні дані на обох шляхах повертають інформативне повідомлення без розкриття деталей про причину відмови.
Процес проведення тренування починається зі створення нової сесії (вручну або на основі шаблону). Після запуску тренування користувач по черзі додає вправи з каталогу, для кожної вправи фіксує підходи з відповідними параметрами (вага, повторення, тривалість або дистанція – залежно від типу відстеження вправи). Після позначення підходу як виконаного сервер автоматично перевіряє, чи встановлено новий особистий рекорд. Після завершення сесії система перевіряє виконання умов глобальних досягнень (загальна кількість тренувань, підходів, піднятої ваги).
Формування шаблону тренування передбачає послідовне додавання вправ, визначення порядку їх виконання та орієнтовного часу відпочинку між підходами для кожної вправи, а також встановлення цільових параметрів підходів. Готовий шаблон зберігається з обраним рівнем видимості (приватний, публічний або для друзів) і стає доступним для запуску нових тренувальних сесій.
Процес ведення журналу харчування охоплює фіксацію прийомів їжі для конкретної дати. Користувач створює прийом із типом (сніданок, обід, вечеря або перекус), після чого додає продукти з бази харчових значень, вказуючи кількість та одиницю виміру. Система автоматично перераховує загальну калорійність прийому та щоденний підсумок макронутрієнтів після кожного доданого позиції. Споживання води реєструється окремим записом, що враховується у зведеному щоденному звіті.
Складання плану харчування полягає у визначенні загальної кількості днів, наповненні кожного дня прийомами їжі та формуванні переліку продуктів із кількостями для кожного прийому. Активація готового плану автоматично деактивує попередній активний план, забезпечуючи одночасну активність лише одного плану.
Перегляд статистики надає зведені показники тренувальної активності за обраний часовий діапазон (кількість тренувань, виконаних підходів, сумарна підіймана вага, середня тривалість сесії), графіки прогресу за окремими вправами, динаміку антропометричних показників, а також перелік особистих рекордів і розблокованих досягнень.
Діаграма діяльностей для описаних сценаріїв взаємодії запланована для розміщення у додатку Д.

3.4. Проєктування бази даних
База даних застосунку відноситься до типу OLTP (Online Transaction Processing, транзакційна обробка даних в режимі реального часу): вона орієнтована на часті короткі транзакції зі створення, читання, оновлення та видалення записів, що відповідає характеру роботи з даними під час тренування або ведення журналу харчування. Обчислювальне середовище побудоване за моделлю клієнт-сервер: централізований сервер PostgreSQL [14] обслуговує всі сервісні модулі серверного застосунку, а доступ до даних здійснюється виключно через шар TypeORM [17].
Для розгортання бази даних планується використання керованого хмарного сервісу Supabase [20], що базується на PostgreSQL. Перевагою цього середовища є вбудований пулінг з'єднань, автоматичне резервне копіювання та підтримка SSL-з'єднань без потреби у ручному адмініструванні. Взаємодія серверного застосунку з базою здійснюється через TypeORM [17] – ORM-фреймворк для TypeScript, який забезпечує декларативне визначення схем через анотації класів-сутностей та версіонування схеми через систему міграцій. Представлення, тригери та збережені процедури у схемі не передбачені – уся бізнес-логіка реалізована на рівні сервісного шару застосунку.
Схема бази даних організована за шістьма тематичними групами сутностей, кожна з яких відповідає певному функціональному домену системи. Нижче наведено опис основних таблиць та їхніх зв'язків.
Перша група – управління користувачами – охоплює облікові записи, антропометричні показники з прив'язкою до типу та одиниць виміру, а також соціальні зв'язки між користувачами з управлінням статусами запитів на дружбу. Друга група – каталог вправ – зберігає структуровану базу системних та користувацьких вправ із класифікацією за типом відстеження, необов'язковим обладнанням і переліком задіяних м'язових груп з відображенням ступеня залучення. Третя група – відстеження тренувань – забезпечує ведення журналу тренувальних сесій на трьох рівнях (сесія, вправа, підхід) та паралельну систему шаблонів, яка дзеркально повторює цю структуру для повторного використання. Четверта група – система досягнень та особистих рекордів – зберігає визначення нагород, факти їх розблокування та найкращі показники користувача по кожній вправі, включно з розрахованим одноповторним максимумом. П'ята група – журнал харчування – охоплює базу продуктів із поживною цінністю, прийоми їжі з прив'язкою до типу та дати, позиції прийомів та записи споживання води. Шоста група – планування харчування – реалізує плани раціону у вигляді ієрархічної структури «план → день → прийом → позиція» з обмеженням на одночасну активність лише одного плану для кожного користувача.
Схему бази даних розроблено з дотриманням третьої нормальної форми (3НФ). Виконання першої нормальної форми (1НФ) забезпечується збереженням атомарних значень у кожному стовпці, відсутністю повторюваних груп атрибутів та наявністю первинного ключа в кожній таблиці. Відсутність часткових функціональних залежностей – вимога другої нормальної форми (2НФ) – досягається використанням сурогатних цілочисельних ключів з автоматичною генерацією значень: оскільки всі первинні ключі є однополеми, часткові залежності структурно неможливі. Для дотримання 3НФ потенційно транзитивні залежності усунуто шляхом виокремлення перерахувальних значень у довідникові таблиці visibility_type, tracking_types, meal_types та units, що виключає аномалії оновлення та гарантує цілісність класифікаторів через зовнішні ключі.
Схема бази даних у вигляді ER-діаграми наведена у додатку E.

3.5. Проєктування інтерфейсу користувача
Проєктування інтерфейсу виконане методом низькодеталізованих прототипів (Low-fidelity Wireframes). Wireframes описаних екранів наведені у додатку Ж.
Навігаційна модель застосунку ґрунтується на панелі вкладок, закріпленій у нижній частині екрана. Три основні вкладки забезпечують прямий доступ до розділів тренувань, харчування, та профілю. Такий патерн є загальноприйнятим стандартом для мобільних фітнес-застосунків і мінімізує кількість кроків, необхідних для переходу між функціональними розділами.
Wireframe головної сторінки тренувань спроєктовано як відправну точку тренувального розділу. Екран містить кнопку для створення нового порожнього тренування, елемент переходу до сторінки шаблонів для запуску сесії на основі наявного шаблону, а також прокручуваний список раніше проведених тренувань із коротким резюме кожного.
Wireframe головної сторінки харчування організований навколо щоденного зведення харчування. На початку екрана розміщений блок щоденного зведення з кільцевою візуалізацією загальної калорійності та окремими індикаторами для білків, жирів і вуглеводів. Цільові значення калорійності та макронутрієнтів визначаються активним планом харчування або задаються користувачем вручну, а за відсутності плану та власних цілей блок відображає лише підсумок спожитого за день без порівняння з ціллю. Поряд відображається поточний обсяг спожитої води з кнопкою швидкого запису. Під зведенням розміщено прийоми їжі, згруповані за типами: кожен прийом відображає загальну калорійність та список продуктів. Прийоми підтримують розгортання для перегляду окремих позицій. Навігація між датами реалізована через елементи управління у верхній частині екрана.
Кольорова схема та загальні принципи відображення визначені нефункціональними вимогами: темна кольорова схема з темно-сірими відтінками та зеленими акцентами для виділення активних елементів і ключових показників. Таке оформлення забезпечує комфортне читання в умовах зниженого освітлення та є типовим для продуктів у фітнес-сегменті.

3.6. Висновки до розділу 3
У третьому розділі виконано комплексне проєктування архітектури та компонентів мобільного застосунку Athlo для персонального планування тренувань та харчування. Для побудови системи обрано клієнт-серверну архітектуру з тришаровим поділом сервера (контролери – сервіси – репозиторії) та модульним принципом організації коду засобами NestJS. Чотири незалежних сервісних модулі (управління користувачами, каталог вправ, тренування, харчування) забезпечують розмежування відповідальності та можливість незалежного розширення кожного з доменів.
Визначено фізичну топологію розгортання: мобільний клієнт React Native / Expo функціонує на пристрої користувача та розповсюджується через сервіс Expo EAS [18], серверний застосунок NestJS розгортається на хмарній платформі Render [19] з автоматичним перерозгортанням при оновленні репозиторію, а база даних PostgreSQL – у керованому середовищі Supabase [20]. Вся міжкомпонентна комунікація захищена шифруванням: клієнт-сервер – через HTTPS, сервер-база даних – через SSL-з'єднання. Схему бази даних спроєктовано як OLTP-систему з 25-ма взаємопов'язаними таблицями, розподіленими за шістьма тематичними групами: управління користувачами, каталог вправ, відстеження тренувань, система досягнень, журнал харчування та планування харчування. ORM-взаємодію з базою забезпечує TypeORM із міграційним підходом до управління схемою.
Виявлено шість ключових сценаріїв взаємодії для подальшого моделювання у вигляді діаграм діяльностей. Було розроблено низькодеталізовані wireframes, що визначають структурне компонування, навігаційну модель та принципи відображення даних. Отримані проєктні рішення є достатньою основою для переходу до безпосередньої програмної реалізації застосунку, описаної у четвертому розділі.
