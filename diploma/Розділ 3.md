РОЗДІЛ 3. ПРОЄКТУВАННЯ МОБІЛЬНОГО ЗАСТОСУНКУ ДЛЯ ПЛАНУВАННЯ ТРЕНУВАНЬ ТА ХАРЧУВАННЯ

3.1. Архітектурне рішення та компонентна структура системи
Архітектурне проєктування є ключовим етапом життєвого циклу програмного забезпечення: прийняті на цьому рівні рішення безпосередньо визначають масштабованість, надійність та зручність подальшого супроводу системи [15]. Для розроблення застосунку Athlo обрано клієнт-серверну архітектуру, яка забезпечує чіткий поділ між рівнем інтерфейсу користувача, рівнем бізнес-логіки та рівнем зберігання даних. Такий підхід дозволяє незалежно оновлювати кожен із компонентів, не порушуючи роботу решти системи, а також спрощує одночасну підтримку двох мобільних платформ. Оскільки застосунок призначений для функціонування на двох мобільних платформах одночасно, клієнт-серверна модель є доцільним вибором: мобільний клієнт відповідає виключно за відображення даних та взаємодію з користувачем, тоді як уся логіка обробки зосереджена на сервері, що мінімізує дублювання коду між платформами.
Архітектура передбачає поділ системи на три логічні рівні з чітко розмежованою відповідальністю. Рівень подання, реалізований мобільним клієнтом, відповідає виключно за відображення даних та обробку дій користувача і не містить бізнес-правил. Рівень застосунку зосереджує всю обробку даних, розрахунки та перевірку правил предметної області. Рівень даних відповідає за надійне зберігання та цілісність інформації. Взаємодія між рівнем подання та рівнем застосунку відбувається через REST API: кожен запит до захищеного ресурсу самостійно несе токен автентифікації, що дозволяє серверу перевірити особу та повноваження запитувача без прив'язки до сесії. Така відсутність серверного стану спрощує горизонтальне масштабування серверної частини у разі зростання навантаження. Клієнтський рівень реалізується засобами React Native та Expo [16], а автентифікація – за стандартом JSON Web Token (JWT) [17].
Рівень застосунку побудований за шаблоном багатошарової архітектури, що впорядковує внутрішню структуру серверної частини. Перший шар – контролери – приймає HTTP-запити, виконує маршрутизацію та первинну валідацію вхідних даних. Другий шар – сервіси – містить основну бізнес-логіку: розрахунки калорійності, перевірку особистих рекордів, присвоєння досягнень. Третій шар – репозиторії – забезпечує взаємодію з базою даних через об'єктно-реляційне відображення. Кожен шар залежить лише від інтерфейсів нижчого шару, що підвищує тестованість, спрощує заміну окремих компонентів та полегшує написання модульних тестів для сервісного шару. Описаний шаровий поділ реалізується засобами фреймворку NestJS [13] із доступом до даних через TypeORM [18].
Серверний застосунок планується поділити на чотири функціонально незалежні модулі, кожен із яких охоплюватиме окремий домен системи та матиме власний набір сервісів і сутностей бази даних. Модуль користувача відповідатиме за реєстрацію, автентифікацію, управління профілем, відстеження антропометричних показників та функції соціальної взаємодії між користувачами. Модуль каталогу вправ надаватиме доступ до структурованої бібліотеки фізичних вправ, обладнання та м'язових груп. Модуль тренувань реалізовуватиме відстеження тренувальних сесій, управління шаблонами тренувань, систему особистих рекордів, досягнень і статистики. Модуль харчування охоплюватиме управління базою продуктів харчування, ведення журналу прийомів їжі, фіксацію споживання води та планування раціону.
Обраний підхід безпосередньо забезпечить реалізацію нефункціональних вимог, сформованих у розділі 2. Масштабованість досягатиметься завдяки незалежності модулів один від одного: розширення функціональності в межах одного модуля не торкатиметься інших, а вузькі місця можна оптимізувати точково. Безпека забезпечуватиметься на кількох рівнях: паролі зберігатимуться у хешованому вигляді з використанням алгоритму bcrypt, JWT-токени [17] обмежуватимуть доступ до захищених ресурсів, а кожна операція зміни або видалення запису супроводжуватиметься перевіркою належності ресурсу поточному користувачу. Зручність підтримки забезпечуватиметься дотриманням принципу розділення відповідальностей: кожен компонент відповідатиме за строго визначене коло завдань, що знижує ризик регресій при подальшому розвитку системи.
Логічна структура компонентів системи та зв'язки між ними представлені у вигляді діаграми компонентів у додатку В.

3.2. Інфраструктурне середовище розгортання
Фізична модель розгортання визначає, яким чином спроєктовані логічні компоненти розподіляються між апаратно-обчислювальними вузлами та мережевою інфраструктурою. Інфраструктура системи охоплює три фізичних рівні: мобільний пристрій кінцевого користувача, сервер застосунку та сервер бази даних, кожен з яких відповідає за окремий аспект функціонування системи.
Клієнтський рівень – це мобільний пристрій користувача під управлінням iOS або Android, на якому функціонує скомпільована збірка React Native / Expo [16]. Для збірки та розповсюдження застосунку використовується хмарний сервіс Expo Application Services (EAS) [19] – складова екосистеми Expo, що дозволяє компілювати нативні бінарні файли для iOS та Android у хмарному середовищі без потреби у локальному налаштуванні збірки, а також забезпечує механізм розповсюдження застосунку серед тестових пристроїв через посилання для встановлення.
Рівень застосунку – це процес Node.js, у якому виконується серверний застосунок на базі NestJS. Сервер приймає вхідні HTTPS-запити від мобільних клієнтів, обробляє їх у відповідних сервісних модулях і повертає структуровані JSON-відповіді з кодами стану, що відповідають семантиці HTTP. Для хостингу серверного застосунку обрано хмарну платформу Render [20], яка підтримує автоматичне перерозгортання при кожному новому push-commit у репозиторій: зміни у вихідному коді автоматично призводять до оновлення запущеного сервісу без ручних операцій, що скорочує цикл доставки нових версій.
Рівень даних представлений реляційною базою даних PostgreSQL [14] – відкритим програмним забезпеченням корпоративного класу, що вирізняється розвиненою підтримкою транзакцій за моделлю ACID, потужними механізмами індексування та широкими можливостями розширення типів даних. Для хостингу бази даних планується використання керованого хмарного сервісу Supabase [21], що надає PostgreSQL-інфраструктуру з вбудованим пулінгом з'єднань, автоматичним резервним копіюванням та SSL-захистом каналу зв'язку, що звільняє від потреби в ручному адмініструванні.
Уся комунікація між мобільним клієнтом та сервером застосунку здійснюється за протоколом HTTPS, що унеможливлює перехоплення даних під час передавання та забезпечує цілісність переданого вмісту. База даних не має прямого зовнішнього доступу – запити до неї надходять виключно від серверного застосунку у межах захищеного мережевого сегменту, що зменшує поверхню можливих атак.
Діаграма розгортання, що відображає розподіл системних компонентів між фізичними вузлами та мережеву топологію, наведена у додатку Г.

3.3. Моделювання ключових сценаріїв взаємодії
Для розуміння динамічної поведінки системи виявлено шість ключових бізнес-процесів: автентифікацію, проведення тренування, створення шаблону тренування, ведення журналу харчування, формування плану харчування та перегляд статистики. Нижче коротко описано послідовність дій у кожному з них.
Сценарій автентифікації охоплює два шляхи. При реєстрації користувач вводить електронну адресу, ім'я, нікнейм і пароль; сервер перевіряє унікальність адреси, створює обліковий запис із хешованим паролем і видає JWT-токен [17]. При вході — вводить адресу й пароль, сервер порівнює хеш і за збігу повертає токен. Помилкові дані в обох випадках повертають інформативне повідомлення без деталей про причину відмови, що ускладнює перебір.
Процес проведення тренування починається зі створення сесії — вручну або з шаблону. Користувач додає вправи з каталогу та фіксує підходи з відповідними параметрами (вага, повторення, тривалість або дистанція) залежно від типу відстеження вправи. Після кожного підходу сервер автоматично перевіряє встановлення нового особистого рекорду, а після завершення сесії — виконання умов глобальних досягнень.
Шаблон тренування формується шляхом послідовного додавання вправ із визначенням порядку виконання, орієнтовного часу відпочинку та цільових параметрів підходів. Готовий шаблон зберігається з обраним рівнем видимості: приватний, публічний або для друзів, що визначає коло користувачів, які матимуть до нього доступ.
Журнал харчування охоплює фіксацію прийомів їжі (сніданок, обід, вечеря, перекус) для конкретної дати. Користувач додає продукти з бази харчових значень, вказуючи кількість та одиницю виміру; система автоматично перераховує калорійність і макронутрієнти пропорційно до вказаної порції. Споживання води реєструється окремо та враховується у зведеному щоденному звіті разом із підсумками за прийомами їжі.
План харчування складається з визначення кількості днів, наповнення кожного дня прийомами їжі та переліку продуктів із кількостями. Активація плану автоматично деактивує попередній, забезпечуючи одночасну активність лише одного плану та усуваючи конфлікти між цільовими показниками.
Перегляд статистики надає зведені показники за обраний діапазон (кількість тренувань, підходів, сумарна вага, середня тривалість), графіки прогресу за вправами, динаміку антропометричних показників, а також особисті рекорди та розблоковані досягнення.
Діаграма діяльностей для описаних сценаріїв взаємодії запланована для розміщення у додатку Д.

3.4. Проєктування бази даних
База даних застосунку відноситься до типу OLTP: вона орієнтована на часті короткі транзакції зі створення, читання, оновлення та видалення записів, що відповідає характеру роботи з даними під час тренування або ведення журналу харчування. Обчислювальне середовище побудоване за моделлю клієнт-сервер: централізований сервер PostgreSQL [14] обслуговує всі сервісні модулі серверного застосунку, а доступ до даних здійснюється виключно через шар TypeORM [18], що уніфікує спосіб взаємодії з базою.
Для розгортання бази даних планується використання керованого хмарного сервісу Supabase [21], що базується на PostgreSQL. Перевагою цього середовища є вбудований пулінг з'єднань, автоматичне резервне копіювання та підтримка SSL-з'єднань без потреби у ручному адмініструванні. Взаємодія серверного застосунку з базою здійснюється через TypeORM [18] – ORM-фреймворк для TypeScript, який забезпечує декларативне визначення схем через анотації класів-сутностей та підтримує міграційний підхід до управління версіями схеми. Представлення, тригери та збережені процедури у схемі не передбачені – уся бізнес-логіка реалізована на рівні сервісного шару застосунку, що спрощує її тестування та подальшу підтримку.
Схема бази даних організована за шістьма тематичними групами сутностей, кожна з яких відповідає певному функціональному домену системи. Нижче наведено опис основних таблиць та їхніх зв'язків.
Перша група – управління користувачами – охоплює облікові записи, налаштування добових цілей харчування, антропометричні показники з прив'язкою до типу та одиниць виміру, а також соціальні зв'язки між користувачами з управлінням статусами запитів на дружбу. Друга група – каталог вправ – зберігає структуровану базу системних та користувацьких вправ із класифікацією за типом відстеження, необов'язковим обладнанням і переліком задіяних м'язових груп з відображенням ступеня залучення. Третя група – відстеження тренувань – забезпечує ведення журналу тренувальних сесій на трьох рівнях (сесія, вправа, підхід) та паралельну систему шаблонів, яка дзеркально повторює цю структуру і підтримує збереження публічних шаблонів у персональну колекцію. Четверта група – система досягнень та особистих рекордів – зберігає визначення нагород, факти їх розблокування та найкращі показники користувача по кожній вправі, включно з розрахованим одноповторним максимумом. П'ята група – журнал харчування – охоплює базу продуктів із поживною цінністю, прийоми їжі з прив'язкою до типу та дати, позиції прийомів та записи споживання води. Шоста група – планування харчування – реалізує плани раціону у вигляді ієрархічної структури «план → день → прийом → позиція» з обмеженням на одночасну активність лише одного плану для кожного користувача.
Для наповнення бази даних планується двокомпонентний підхід. Перший компонент — скрипт ініціалізації, який заповнює допоміжні довідники (типи видимості, типи відстеження вправ, одиниці виміру тощо) та генерує демонстраційні дані для перевірки коректності розгортання. Другий — ETL-пайплайн для масового завантаження реального контенту із зовнішніх API: каталогу вправ із анімаціями та бази харчових продуктів. Пайплайн нормалізуватиме отримані дані відповідно до схеми бази даних і виконуватиме їх безпечне збереження з контролем дублікатів. Це забезпечить готову бібліотеку вправ і продуктів одразу після розгортання та зменшить кількість звернень до зовнішніх сервісів у процесі роботи застосунку.
Схема бази даних у вигляді ER-діаграми наведена у додатку E.

3.5. Проєктування інтерфейсу користувача
Проєктування інтерфейсу виконане методом низькодеталізованих прототипів (Low-fidelity Wireframes), що дозволяє зосередитися на структурному компонуванні екранів і логіці навігації без відволікання на деталі візуального оформлення. Wireframes описаних екранів наведені у додатку Ж.
Навігаційна модель застосунку ґрунтується на панелі вкладок, закріпленій у нижній частині екрана. Три основні вкладки забезпечують прямий доступ до розділів тренувань, харчування, та профілю. Такий патерн є загальноприйнятим стандартом для мобільних фітнес-застосунків і мінімізує кількість кроків, необхідних для переходу між функціональними розділами незалежно від поточного контексту користувача.
Wireframe головної сторінки тренувань спроєктовано як відправну точку тренувального розділу. Екран містить кнопку для створення нового порожнього тренування, елемент переходу до сторінки шаблонів для запуску сесії на основі наявного шаблону, а також прокручуваний список раніше проведених тренувань із коротким резюме кожного, що дозволяє швидко повернутися до перегляду історії.
Головний екран харчування організований навколо щоденного зведення: кільцева діаграма калорійності, індикатори макронутрієнтів (білки, жири, вуглеводи) та поточний обсяг спожитої води з кнопкою швидкого запису. Цільові значення беруться з активного плану або задаються вручну; за їх відсутності відображається лише фактичний підсумок. Нижче — список прийомів їжі, згрупованих за типами, із загальною калорійністю та розгортанням для перегляду окремих продуктів. Навігація між датами розміщена у верхній частині екрана, що дозволяє швидко переходити між днями журналу.
Кольорова схема та загальні принципи відображення визначені нефункціональними вимогами: темна кольорова схема з темно-сірими відтінками та зеленими акцентами для виділення активних елементів і ключових показників. Таке оформлення забезпечує комфортне читання в умовах зниженого освітлення, зменшує навантаження на органи зору при тривалому використанні та є типовим для продуктів у фітнес-сегменті.

3.6. Висновки до розділу 3
У третьому розділі виконано комплексне проєктування архітектури та компонентів мобільного застосунку Athlo для персонального планування тренувань та харчування. Для побудови системи обрано клієнт-серверну архітектуру з тришаровим поділом сервера (контролери – сервіси – репозиторії) та модульним принципом організації коду засобами NestJS. Чотири незалежних сервісних модулі (управління користувачами, каталог вправ, тренування, харчування) забезпечують розмежування відповідальності, спрощують модульне тестування та відкривають можливість незалежного розширення кожного з доменів.
Визначено фізичну топологію розгортання: мобільний клієнт React Native / Expo функціонує на пристрої користувача та розповсюджується через сервіс Expo EAS [19], серверний застосунок NestJS розгортається на хмарній платформі Render [20] з автоматичним перерозгортанням при оновленні репозиторію, а база даних PostgreSQL – у керованому середовищі Supabase [21]. Вся міжкомпонентна комунікація захищена шифруванням: клієнт-сервер – через HTTPS, сервер-база даних – через SSL-з'єднання. Схему бази даних спроєктовано як OLTP-систему з 25-ма взаємопов'язаними таблицями, розподіленими за шістьма тематичними групами: управління користувачами, каталог вправ, відстеження тренувань, система досягнень, журнал харчування та планування харчування. ORM-взаємодію з базою забезпечує TypeORM із міграційним підходом до управління схемою, що дозволяє контролювати її версії разом із вихідним кодом.
Виявлено шість ключових сценаріїв взаємодії для подальшого моделювання у вигляді діаграм діяльностей. Було розроблено низькодеталізовані wireframes, що визначають структурне компонування, навігаційну модель та принципи відображення даних, які стануть основою для подальшої деталізації візуального оформлення.
