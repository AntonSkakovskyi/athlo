# Git & Commit Standards

Цей документ визначає правила роботи з Git у нашому монорепозиторії. Всі повідомлення комітів мають бути структурованими, лаконічними та інформативними.

## 1. Формат повідомлення (Commit Message Format)
Використовуй наступну структуру для кожного коміту:
`<scope>: <short description in English>`

### Дозволені Scope (Області):
* **api**: Зміни в бекенді (NestJS).
* **mobile**: Зміни у фронтенді (React Native/Expo).
* **shared**: Зміни в спільному пакеті типів (`@athlo/shared`).
* **monorepo**: Глобальні налаштування (CI/CD, root package.json, Docker).
* **docs**: Зміни в документації або `.md` файлах.

## 2. Приклади правильних комітів
* `api: implement jwt login logic`
* `mobile: add workout tracking screen`
* `shared: add IWorkout interface`
* `api: add validation for register dto`
* `mobile: fix splash screen scaling`
* `monorepo: update github actions for deploy`

## 3. Правила написання (Best Practices)
* **Мова**: Використовуй англійську мову (Imperative mood — наказовий спосіб). Пиши "add feature", а не "added feature" або "adds feature".
* **Довжина**: Перший рядок (заголовок) не повинен перевищувати 50-60 символів.
* **Суть**: Коміт має відповідати на питання "Що цей код змінить?", а не "Які файли я редагував".
* **Атомарність**: Один коміт = одна завершена задача. Не змішуй рефакторинг бекенду з виправленням стилів на фронті в одному коміті.

## 4. Стратегія роботи з гілками (Workflow)
* **Прямолінійна історія**: Використовуй `git pull --rebase` перед пушем, щоб уникнути зайвих "Merge branch..." комітів.
* **Main branch**: Гілка `main` (або `master`) завжди має бути в робочому стані.
* **Feature branches**: Для кожної фази плану (`Phase 1`, `Phase 2`) створюй окрему гілку, наприклад `feat/phase1-auth`.

## 5. Інструкція для ШІ
Перед кожним комітом, якщо я прошу тебе "згенерувати повідомлення для коміту", ти повинен:
1. Проаналізувати змінені файли.
2. Визначити правильний `scope`.
3. Сформувати коротке повідомлення згідно з цими правилами.
