# React Native & Expo Development Standards

Цей документ визначає стандарти написання коду для забезпечення масштабованості та підтримки проєкту. Дотримуйся цих правил при генерації будь-якого фронтенд-коду.

## 1. Архітектура та Структура
* **Feature-based structure**: Розділяй логіку за функціоналом (auth, workouts, profile).
* **Separation of Concerns**: 
    * **UI (Components)**: Тільки відображення та базова обробка подій.
    * **Logic (Hooks)**: Вся бізнес-логіка, запити до API та робота зі стейтом виносяться у кастомні хуки.
    * **Services**: Прямі виклики до API (axios/fetch).

## 2. Компоненти та Стилізація
* **Atomic Design (спрощений)**: Створюй маленькі перевикористовувані UI-елементи в `/components/ui`.
* **Props**: Використовуй сувору типізацію для props через TypeScript (інтерфейси).
* **Styling**: Використовуй `StyleSheet.create` або Tailwind (NativeWind), якщо він підключений. Уникай інлайнових стилів.
* **Responsiveness**: Використовуй гнучку розмістку (flexbox) та уникай жорстко прописаних `width/height` у пікселях, де це можливо.

## 3. Робота з даними (React Query)
* **Query Keys**: Використовуй централізований об'єкт `queryKeys` для уникнення магічних рядків.
* **Hooks**: Кожен запит (GET) або мутація (POST/PUT/DELETE) має бути у власному хуку в папці `hooks/api`.
* **Error Handling**: Передбачай стан завантаження (`isLoading`) та помилки (`error`) у кожному UI-компоненті.

## 4. TypeScript та Типізація
* **No `any`**: Використання `any` суворо заборонено.
* **Shared Types**: Спільні моделі даних (наприклад, `User`, `Workout`) мають зберігатися в папці `types/` або `api/types.ts`.
* **Type Safety**: Завжди типізуй відповіді від API.

## 5. Навігація (Expo Router)
* Використовуй файлову систему `app/` для роутингу.
* Використовуй типізовані посилання та метод `router.push()`.
* Групуй маршрути: `(auth)` для авторизації, `(app)` для основного функціоналу.

## 6. Найменування (Naming Convention)
* **Компоненти**: PascalCase (`WorkoutCard.tsx`).
* **Хуки**: camelCase з префіксом use (`useWorkoutData.ts`).
* **Константи**: UPPER_SNAKE_CASE.
* **Файли стилів/утиліт**: camelCase.

## 7. Декомпозиція сторінок на підкомпоненти
* **Обов'язково розбивай сторінки на підкомпоненти** — кожна сторінка (screen) має бути тонким "оркестратором", а великі секції виносяться у окремі компоненти поруч.
* **Структура файлів**: Головний файл сторінки лежить як `screen-name.tsx`, а допоміжні компоненти — у папках поруч:
  ```
  app/(app)/
    workout-summary.tsx
    workout-summary/
      OverviewCards.tsx
      ExerciseResultsList.tsx
      SummaryFooter.tsx
  ```
* **Принцип**: Якщо секція сторінки перевищує ~80-100 рядків або може бути перевикористана в іншому місці — виноси її в окремий компонент.
* **Іменування папки**: Папка з підкомпонентами називається так само, як і файл сторінки (без розширення).
* **Іменування компонентів**: PascalCase, кожен компонент в окремому файлі (`ComponentName.tsx`).
* **Перевикористання**: Якщо підкомпонент використовується на кількох сторінках — переноси його до `components/` (ui або feature-based).
* **Виноси логіку в сервіси/utils**: Обчислення, форматування, трансформації даних та іншу бізнес-логіку, яка не стосується рендерингу, виноси у файли `services/` або `utils/` — не прописуй її напряму в компонентах чи сторінках.

## 8. Використання атомарних UI-компонентів (ОБОВ'ЯЗКОВА ВИМОГА)

> **Правило**: Ніколи не пиши inline-примітиви там, де вже існує або може існувати атомарний компонент.

### 8.1 Алгоритм для кожного UI-елемента
Перед тим як написати будь-яку кнопку, інпут, чіп або інший базовий елемент, виконай наступний порядок дій:

1. **Перевір `components/ui/`** — чи існує вже готовий компонент?
2. **Якщо є** — імпортуй та використовуй його. Не дублюй.
3. **Якщо немає** — спочатку створи компонент у `components/ui/`, а потім використовуй звідти.

### 8.2 Поточна бібліотека атомів (`components/ui/`)

| Компонент | Коли використовувати |
|---|---|
| `<Button>` | Будь-яка кнопка з текстом та дією. Варіанти: `primary`, `secondary`, `danger`, `ghost`. Підтримує `isLoading`, `disabled`, `icon`. |
| `<Input>` | Будь-яке текстове поле вводу. Підтримує `label`, `error`. |
| `<Chip>` | Одиночний тег / фільтр-відмітка. Варіанти: `active` / `default`. |
| `<SegmentControl>` | Перемикач вкладок (2–4 сегменти). Використовується замість кастомних tab-switcher. |
| `<EmptyState>` | Порожній стан: ілюстрація + текст + опціональна CTA-кнопка. |

### 8.3 Заборони
* **Заборонено** писати `<Pressable>...<Text>Кнопка</Text></Pressable>` там, де підходить `<Button>`.
* **Заборонено** писати `<TextInput>` безпосередньо в сторінці або компоненті без обгортки `<Input>`.
* **Заборонено** реалізовувати логіку вибору/active-стану для чіпів вручну, якщо є `<Chip active>`.
* **Заборонено** дублювати стилі (фон, border-radius, розмір шрифту) для елементів, що вже описані в атомах.

### 8.4 Коли створювати новий атом
Якщо потрібен UI-примітив, якого ще немає в `components/ui/`:
1. Створи файл `components/ui/NewComponent.tsx`.
2. Продумай усі необхідні `variant` та `props` одразу (орієнтуйся на FIGMA_DESIGN_PLAN.md).
3. Застосуй токени з `constants/theme.ts` (`colors`, `spacing`, `borderRadius`) — ніяких хардкодів.
4. Після створення — одразу використай у поточному завданні.

## 9. Найкращі практики (Clean Code)
* Принцип **DRY** (Don't Repeat Yourself).
* Принцип **KISS** (Keep It Simple, Stupid).
* Використовуй `Optional Chaining` (`?.`) та `Nullish Coalescing` (`??`).
* Додавай JSDoc коментарі для складних функцій.
